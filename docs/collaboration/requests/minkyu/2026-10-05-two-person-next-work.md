# 민규·종현의 다음 병렬 작업

작성자 minkyu. 전체 목표는 출시까지이며 현재 추정57%를 유지한다. 각 기능 구현과 실제 연결/기기/운영 증거를 구분한다. 아래는 민규 현재 작업 트리의 읽기 결과와 담당 정책에 따른 다음 작업 묶음이며 종현의 아직 공유되지 않은 변경을 미구현으로 단정하지 않는다.

## 지금 나눌 두 묶음

| 작업자 | 바로 진행할 한 묶음 | 완료 산출물 |
|---|---|---|
| 민규 | 완료 전 신고 검토 보류와 최초 완료/후기 기한 연결 |40900 후보·실제 SQL/RPC 회귀·연결 계약. 전체 일반 신고를 자동 분쟁 처리하지 않으며 owner 검토 구조와 직원/API 권한을 구분한다. |
| 종현 | 기존 상주 queue 실행기를 검증된 DB/HTTP 계약에 연결 |전용LOGIN 역할 전환·재접속 LISTEN/재조회·세 종류 dispatch·cleanup DTO/claimed0·시간/fence/실패복구 검증. 새 중복 실행기를 만들지 않는다. |

민규의 약속 결과원장 연결40800은 실제 로컬65개 적용·회원API14그룹·원장/취소 실제두세션3경합/정리까지 통과했다. DB 계약은 이를 기준으로 이어간다. 실제 전용LOGIN/TLS의 별도 로컬 증거도 있지만 종현 제품 실행기 연결 성공과 구분한다.

현재 민규 트리의 queue-runner는 SET ROLE 연결·cleanup 분기와 DTO 연결이 남아 있다. 종현은 [구체 연결 요청](2026-10-05-worker-queue-login-runner-connection.md)에 대응하는 자기 소유 파일과 테스트만 수정한다. 민규의 DB/공통 파일 변경이 필요하면 종현 자기 requests 폴더에 정확한 인자/반환/오류·SQL 초안을 남기고 민규가 통합한다. 소유권 정책이나hook을 바꾸어 우회하지 않는다.

## 기다리지 않고 진행할 연결 방식

1. 각자 별도clone/worktree·브랜치·로컬 검증 DB를 쓴다. 같은 폴더/Git 인덱스/테스트 데이터 삭제 영역을 공유하지 않는다. 설정은 본인clone에서 yumidang.actor와 기존hook 상태를 읽고 담당대로 확인한다.
2. 시작할 때 입력·반환·오류·권한·멱등의 연결 계약을 고정한다. DB/HTTP 작업이 아직 없으면 해당 계약의 가상 응답으로 자기 기능을 끝까지 만들며 실제 성공으로 표시하지 않는다.
3. 한 번에 맡는 결과물은 독립 검증 가능한 기능 한 묶음으로 제한한다. 큰 영역 전체가 끝나기를 기다리지 않고 검토할 변경을 작은 단위로 공유한다. 커밋/푸시 전 본인 staged 소유권을 확인한다.
4. 하루 두 번 연결 상태를 확인하는 작업 방식을 제안한다. 확인 내용은 완료 산출물·검증 증거·상대에게 필요한 연결·정책 질문뿐이다. 상대가 진행할 수 있는 작업은 계속하며 새 정책 선택을 코드로 추정하지 않는다.
5. 변경된 기능의 의미 있는 검사→해당 연결 회귀 순으로 실행하고, 같은 바이트의 이미 통과한 전체 검사를 반복하지 않는다. 광범위 회귀는 공통 변경/실패/통합 검토에 필요한 때 수행한다. 파일 존재·합성 테스트수로 실제 운영 완료를 주장하지 않는다.

검토 후 공유하는 변경에는 변경 파일, 검증 명령/범위, source SHA 또는 commit, 필요한 설정 이름, 남은 조건을 포함한다. 비밀키/DB 비밀번호는 문서·메시지·Git에 넣지 않는다. 종현 문서·파일은 민규가 수정하지 않는다. 실제 공유되지 않은 민규 작업트리 변경은 종현clone에 자동 반영되지 않으므로 기능 단위로 공유할 때 적용 버전/마이그레이션을 명시한다.

## 두 묶음 다음

민규는 본인 제재 사유/이의 연결·운영 RPC/권한과 기존 서비스 HTTP를 이어간다. 종현은 검색/행사/AI의 실제 DB 통합과 모바일 연결을 이어간다. 함께 검증할 첫 시나리오는 로그인→공고/검색→신청/확정→일정변경→완료/후기다. 탈퇴·차단·신고는 실패/복귀 흐름까지 확인한다.

Railway 프로젝트/서비스와 배포 담당, 실제 공급사 한도/보관 회신, 법적 검토·실기기는 코드와 별도 완료 조건이다. 현재팀 확인 대기를 코드 작업 전체의 중단 사유로 확대하지 않는다. 배포/운영 권한을 임의 생성하지 않는다. 검토 중 양쪽 일정변경 후 완료 기준은 사용자 답변 대기이며 나머지 보류/원장 구현은 독립 진행한다.
