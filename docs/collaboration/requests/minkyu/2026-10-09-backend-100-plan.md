## 1. 목표와 판정 기준

현재 확정된 무료 1:1 동행 서비스의 백엔드를 **기능 구현 → 실제 서버 연결 → 장애·권한 검증 → 실제 회원 흐름 → 배포·복구·지원 운영**까지 완료한다. 코드 존재, 모형 테스트, SQL 적용 준비, 격리 복원만으로 전체 100%를 판정하지 않는다.

기준은 최신 사용자 결정과 [정책](../../../../정책.md), [최신 계획](../../../../PLAN.md), [상세 설계](../../../../PLAN_상세설계.md)의 담당·연결 계약이다. IA·사용자 흐름의 오래된 문구와 골격 TODO는 최신 결정에 맞춰 담당 파일에서 동기화한다. 네이버 가입·무료 서비스가 최신 기준이며 과거 PASS·문자 로그인·유료 계좌 인증을 현재 범위에 다시 추가하지 않는다.

완료 판정은 아래 세 조건을 모두 만족해야 한다.

1. 4장의 기능별 완료 조건이 실제 서버·DB·Storage·허용된 공급사 연결 증거로 충족된다.
2. 기존 운영 완료 7단계가 모두 닫혀 **7/7**이 된다. 단계별 부분 PASS는 해당 단계 전체 완료와 구분한다.

앱 화면 재설계·스토어 제출·Apple 계정 생성, 현재 제외된 유료 동행·결제·정산은 백엔드 완료 분모에 추가하지 않는다. 앱이 백엔드 오류·권한·인증 복귀를 올바르게 소비하는 통합 검증은 포함한다. 서울 수집·KOPIS 공식 순위·회원 AI 등 이미 목표에 포함되고 보류된 기능은 계속 남긴다.

### 3.1 제품 실행기의 필수 범위

- 실제 지원 종류는 `review_summary`, `event_sync`, `member_cleanup`, `cancellation_safety`, `report_retention`이다. 종류별 입력·권한·실패·상태 전이·복구를 제품 조립 경로에서 검증한다. 미지원 종류는 claim하지 않고 재-enqueue·종류 간 공정성을 확인한다.
- 같은 global run에서 고유 queue jobId 최대20, 원래 최대 실행시간180초를 유지한다. 자동 연장·토큰 재획득으로 한도를 우회하지 않는다. 배정량·남은 시간·AbortSignal을 실제 하위 호출까지 전달한다. DB·Storage 호출 수와 AI 토큰 예산은 별개이며 새 제한을 임의로 만들지 않는다.
- helpful/terminal은 정해진 별도 예산을 사용한다. helpful HTTP 본문 `{limit}`를 유지하고 global token·영속 requestId 헤더를 연결한다. 응답 유실 뒤 같은 키의 결과를 조회하며 새 키로 같은 변경을 반복하지 않는다.
- SQL101 legacy UNKNOWN, SQL102 external_pending, SQL107 member dispatch, SQL108 ACK 읽기 복구를 함께 고려한다. lease 만료·시간 경과·응답 관찰만으로 ACK 확정이나 재삭제를 허용하지 않는다. 최신114 영속 호출·115 원ACK 조회 복구·118 발견/자동 종결 연결을 기준으로 이전 상태의 안전성을 확인한다. 대체된108 호출 자체를 다시 여는 것을 완료 조건으로 추가하지 않는다. legacy101 단독 observed_response가 현재 CLI에서 새 전송 없이 보존되는 경계는 별도 실제 검증한다.
- completion 예약 실행기는 자동 완료·후기 공개의 실제 기한을 처리한다. 행사 수집의 매일00:01 한국시간 배치를 이유로 완료·후기 공개를 하루 단위로 늦추지 않는다.

### 3.2 운영 적용의 필수 범위

- completion 전용 LOGIN, queue 전용 LOGIN/그룹, 서버 내부 비밀을 분리한다. 필요한 RPC 외 PUBLIC 상속·schema/table/column/sequence·다른 함수·역할 승격까지 실효 권한을 검사한다. LISTEN은 지원되는 direct/session 연결과 운영 CA·호스트 검증을 사용한다.
- Railway 환경값을 채우고 재시작하는 것만으로 완료 처리하지 않는다. completion/queue 각각의 시작 명령·배포 버전·역할·채널·guard·READY를 확인한다. 테스트 CA·bootstrap 설정을 운영에 복사하지 않는다.
- SQL100~108 기존 내용을 보존하고 필요한 추가 변경은 후속 migration으로 작성한다. 검토한 순서대로 하나씩 결과를 확정하고, 오류/UNKNOWN 발생 시 다음 변경·재전송을 멈추고 조회로 해결한다.
- 백업은 DB metadata뿐 아니라 역할·Storage 실제 바이트를 포함한다. 쓰기/worker 제어를 통한 일관 지점을 잡고 별도 환경에 복원한다. 오래된 백업의 이미 삭제된 자료는 최소 삭제 기록으로 다시 파기하며 미확정 삭제는 보존한다. 접근 제한된 백업·영수증에서 비밀과 회원 원문 노출을 막는다.
- queue 지연·예약 지연·UNKNOWN·재시작·파기 지연·예산 불일치를 운영 지표로 확인하고 대응 담당·중지/복구 순서를 기록한다. AI 대화·공급사 원응답·비밀값은 진단 로그에 남기지 않는다.

### 4.1 AI 계정·전체 예산의 특별 검증

계정당 한국시간 하루 **320만 토큰**, 전체 상한은 **실제 등록 계정별 상한의 합계**다. 네 계정이 실제 등록되면1,280만이지만 등록되지 않은 계정 용량을 미리 더하지 않는다. 오래된 포함량50% 표현을 적용하지 않는다.

모델 전송 전에 계정별·전체 예산을 원자 예약한다. 해당 계정 부족 시 전송 전에 다음 계정을 선택하며 전체 부족 시 새 호출을 중단한다. 전송 후 인증/권한 오류·timeout·응답 유실을 소진으로 간주해 자동 계정 전환하지 않는다. 한국시간 자정 전후 원 요청의 계정/날짜에 늦은 정산을 연결하고 미확인 예약을 임의 해제하지 않는다. 실제 공급사 초기화 시간·사용량 단위·지정 모델과 제공 모델·출력 상한·차감/공동 사용 조건을 증거로 확인한다. 예약량·공급사 보고량·실제 청구를 분리한다.

### 4.2 보관·파기의 특별 검증

- 탈퇴 프로필/사진은 즉시 파기 대상으로 처리한다. 남은 당사자 채팅은 마지막 활동/절차 중 늦은 시점+1년, 탈퇴 공고 본문은1년과 민감정보 제외 기준을 적용한다.
- 신고는 최종 종결+90일, 제재 상세는 제재 종료/이의 종료 중 늦은 시점+90일, helpful은 접수+90일 또는 회원 탈퇴 중 먼저 발생한 시점에 파기한다.
- 확정 runtime 상세는 완료+30일 후 파기하되 필요한 최소 멱등 기록·미확정 external_pending을 보존한다. 최소키 TTL 미정은 임의 확정/활성화하지 않는다.
- 진단30일/보안90일·비용 원장 공급사 기간 종료+90일 기준을 해당 로그/원장에 적용하고 미정산은 유지한다. 선택한 기간을 법정 기간이라고 안내하지 않는다. 공급사/백업 실제 보관·만료 조건은 별도 확인한다.

## 6. 팀 구성·담당 경계
