범위는 행사 목록·상세·공고 연결·직접 입력과 그에 따른 오류·수정 흐름입니다. 이미 확정한 것은 다시 묻지 않습니다.

각 항목은 A·B·C 세 안 + D 기타 직접 작성입니다. 추천안도 미리 선택하지 않았습니다. 예시는 설명을 위한 가상 상황입니다.

기타를 고르면 원하는 기준을 입력해 주세요. 추천안을 수정하고 싶으면 해당 안을 선택한 뒤 추가 의견을 적어도 됩니다. 답변이 완료된 뒤 정책·PRD·IA·USERFLOW·설계·계약·인수인계 등 관련 문서를 담당 구분 없이 동기화합니다. 지금 저장하는 것은 답변이며 구현·배포가 아닙니다.

같은 브라우저에는 자동 저장됩니다. 파일을 이동하거나 다른 도구에 전달하려면 ‘작성본 HTML 저장’을 사용하세요. 일부 브라우저에서 자동 저장이 안 되더라도 작성본 저장은 사용할 수 있습니다.

이미 확정한 내용 보기 — 다시 고르지 않습니다
  1. 행사명: 목록 최대2줄·넘치면 말줄임, 상세 전체 표시.
  2. 행사 기간: 하루/같은 해 여러 날/해를 넘는 기간 구분, 진행 중·예정·종료 표시. 기간 상태는 개장·예약 가능 보장이 아님.
  3. 행사 카드: 이미지(있을 때)→종류·상태→행사명→기간→지역·행사장→요금. 이미지 없거나 로딩 실패면 빈 영역 없이 글만.
  4. 카드 장소는 지역·행사장, 상세는 공개 전체 행사장 주소. 상세주소를 행사장명으로 오인하지 않음.
  5. 요금: 명시 무료/명확한 단일 금액/요금 상세 확인/요금 정보 없음. 빈 값을 무료로 표시하지 않음.
  6. 분류명: 클래식·국악·무용으로 통일. 명확하게 대응하는 분류만 통일하고 세부 분류 없으면 행사 등 넓은 이름 사용.
  7. 상세 순서: 이름·분류·상태→대표 이미지→기간·시간·장소·주소·요금→소개→제공된 추가 안내→유효 공식/예매 링크→연결 공고.
  8. 필수 성격의 기본 정보는 누락 안내, 출연·프로그램 등 선택 추가 항목은 없으면 생략. 원천 없는 정보나 링크를 생성하지 않음.
  9. 행사 상세→동행 구하기는 해당 행사 사전 연결. 일반 공고 작성에서도 검색·목록에서 연결하거나 직접 입력하거나 연결 없이 작성 가능.
  10. 행사 영역은 작성 화면 위에 둠. 버튼 이름은 변경·삭제. 삭제는 그 공고의 연결만 제거하며 행사 자체를 삭제하지 않음.
  11. 직접 입력: 행사명 필수·장소명/공개 행사장 주소 선택. 별도 행사 기간·요금·이미지 입력 없음. 필요한 설명은 공고 소개에 작성.
  12. 직접 입력 행사는 해당 공고에만 표시. 공통 행사 목록·독립 상세·검수 후 공용화 절차 없음. 개인 취미 공연·외부 원데이클래스도 가능.
  13. 직접 입력 주소 선택과 공고의 필수 만남 장소는 별개. 공개 행사장 주소와 확정 당사자만 보는 상세 만남 지점도 분리.
  14. 공고의 연결 행사 카드는 종류·행사명·행사기간·행사장·이미지(있을 때)를 요약하고 API 행사는 행사 상세로 이동. 연결 없으면 영역 생략.
  15. 연결 공고는 내부 행사 식별자 관계로 조회. 제목이 비슷하다는 이유로 연결하지 않음. 외부 행사 API는 유미당 동행 공고를 제공하지 않음.
  16. 취소·연기는 의미가 확인된 공식 원천 상태만 표시. 취소된 행사 새 선택 불가와 취소된 행사예요 문구 확정. 약속 자동 취소 없음.
  17. 새 연결: 예정·진행 중 가능, 종료·취소 불가, 연기 일정 미정 불가, 변경 일정 확인 시 조건에 맞으면 가능, 비표출은 새 선택 제외.
  18. 원천 기간·장소가 갱신돼도 기존 동행 약속은 자동 변경하지 않음. 단순 검색 누락은 취소·삭제·비표출의 증거가 아님.
  19. 확인된 비표출은 A안: 연결된 행사 정보를 현재 제공할 수 없어요. 행사 취소를 의미하지는 않아요. 원천명·이미지·설명·주소와 상세 이동 숨김, 공고·약속·내부 연결 유지. 직접 입력에는 적용하지 않음.
  20. 등록 직전 상태 재확인과 입력 보존. 취소 등 연결 불가가 확인되면 변경·삭제 안내. 확인 실패 처리만 E05에서 선택.
  21. 서울 HTTPS·자동 수집은 민규 서버 작업. KOPIS 집계기간 대조와 별개로 다른 API·화면 작업 진행. 지금 추가 호출·배포·메시지 전송하지 않음.
E01 · 선택 필요

행사부터 고른 뒤 만남 시간을 정해도 될까요?

대조 근거: 정책 8장 작성용 일정 겹침 · IA S03/S09-2 · 현재 RemoteEventPicker · 최신 대화의 최상단 행사 영역

왜 정하나요?

행사 영역은 작성 화면 맨 위로 정했습니다. 그런데 기존 화면과 정책은 만남 시간을 먼저 입력해야 겹치는 행사를 선택할 수 있습니다. 겹쳐야 한다는 기준을 바꾸는 질문이 아니라, 고르는 순서와 확인 시점을 정하는 질문입니다.

예시로 보면

11월 1일 뮤지컬을 먼저 고른 뒤, 만남 시간을 11월 5일로 입력하면 날짜가 맞지 않습니다. 행사 선택 때문에 작성한 날짜를 자동으로 바꾸지는 않습니다.

함께 알아둘 점

세 안 모두 기존 일정 겹침 조건 유지. 직접 입력한 행사는 행사 기간을 받지 않으므로, 공고의 필수 만남 일정 기준으로 처리하며 존재하지 않는 행사 기간을 만들어 검사하지 않습니다.

E02 · 선택 필요

행사 검색·선택 화면은 어디까지 찾아줄까요?

대조 근거: 정책 4-1의 10개 더보기·빈 결과/오류 구분, 8장의 주간 기본 목록 · 현재 선택창의 검색 UI 미지원

왜 정하나요?

일반 행사 목록 기본은 이번 주 신규 중 미종료로 이미 확정됐습니다. 그러나 다음 주 행사를 찾는 검색과 작성용 선택창까지 이번 주에 가둘지는 정하지 않았습니다.

예시로 보면

이번 주에는 안 열리지만 다음 주에 열리는 전시회를 검색해 공고에 연결하려는 상황입니다.

함께 알아둘 점

전체는 전국의 모든 행사가 아니라 우리 서버가 실제 조회 가능한 자료 범위입니다. 10개씩 더보기·조회 실패와 0건 구분·진행 중 포함·과거 조회는 기존 기준을 유지합니다. 오류가 났다고 해당 행사가 없다고 안내하지 않습니다.

E03 · 선택 필요

TourAPI의 영화·스포츠경기·박람회도 행사로 보여줄까요?

대조 근거: 첨부 분류 연계표 A20:I39: 축제6·공연10·행사4 · 정책 8장 제공처 실제 분류 원칙

왜 정하나요?

TourAPI 관광타입 15에는 축제·공연뿐 아니라 전시회·박람회·스포츠경기도 정의돼 있습니다. 분류표에 존재한다는 사실과 유미당에서 포함하기로 한 것은 다릅니다.

예시로 보면

TourAPI에서 야구 경기나 박람회가 실제로 들어오면 일반 행사 목록과 행사 선택창에도 보여줄지의 문제입니다.

함께 알아둘 점

원데이클래스·개인 취미 공연의 직접 입력 허용은 이미 확정돼 유지합니다. 시설 타입14를 행사로 확대하지 않습니다. 외부 입장료·수강료와 무료 1:1 동행은 별개이며 플랫폼 결제·유료 동행을 도입하는 선택이 아닙니다.

E04 · 선택 필요

같은 행사가 기관마다 따로 있으면 어떻게 보여줄까요?

대조 근거: 행사 매핑 provider+sourceId 및 중복 자동 병합 금지 · 최신 대화의 같은 행사 연결 공고 표현 보완

왜 정하나요?

현재는 기관과 원천 ID가 다르면 별도 행사입니다. 제목이 같다는 이유로 자동 통합하지 않습니다. 그래서 현실에서는 같은 축제여도 연결 공고가 기관별로 나뉠 수 있습니다.

예시로 보면

TourAPI의 서울축제에 공고2개, 서울 열린데이터의 서울축제에 공고3개가 연결되면 지금 구조로는 각각2개와3개를 보여줍니다.

함께 알아둘 점

B/C는 새로운 서버·데이터 관리 범위입니다. 기존 자동 병합 금지를 단순 문자열 비교로 우회하지 않습니다. 선택만으로 연결표가 확보되거나 실제 통합이 완료되는 것은 아닙니다.

E05 · 선택 필요

공고 등록 직전 행사 상태를 확인하지 못하면요?

대조 근거: 최신 대화의 등록 시 재확인·입력 보존 · 공고 행사 연결은 선택이라는 정책

왜 정하나요?

취소·종료·비표출처럼 연결 불가가 확인된 경우의 처리는 정했습니다. 이번 질문은 우리 서버에 연결되지 않아 확인 자체가 실패한 경우입니다.

예시로 보면

공고를 다 쓴 뒤 등록을 눌렀는데 통신 오류로 연결 행사의 현재 상태를 확인하지 못했습니다.

함께 알아둘 점

등록할 때마다 외부 기관 API를 직접 호출하자는 뜻이 아닙니다. 우리 서버의 최신 저장 정보와 연결 가능 여부를 검증합니다. 선택 행사나 작성 글을 사용자 모르게 삭제하지 않습니다.

E06 · 선택 필요

기관이 취소 상태 항목 자체를 제공하지 않는 경우는요?

대조 근거: 행사 매핑 G01: KOPIS 진행 상태는 취소 여부와 다름·서울 명시 상태 없음 · 현재 서버 unknown 공개 제한

왜 정하나요?

취소라고 명시된 것, 조회 오류, 기관이 취소 여부를 아예 제공하지 않는 것은 다릅니다. 마지막 경우까지 막으면 기간·장소는 받아도 일부 기관의 행사를 전혀 연결할 수 없게 됩니다.

예시로 보면

정상적으로 수집한 행사에 시작일·종료일은 있지만 취소 여부를 알려주는 칼럼이 없는 상황입니다.

함께 알아둘 점

API 호출 실패·손상된 값·상태 해석 실패를 정보 미제공으로 바꿔 허용하지 않습니다. 실제 원천 값의 의미 확인은 선택과 별도의 기술 검증입니다. A/C는 unknown을 active로 조작하는 것이 아니라 미제공 상태를 구분할 서버 계약 보완이 필요합니다.

E07 · 선택 필요

행사 상세의 연결 공고는 어떤 순서·범위로 보여줄까요?

대조 근거: 정책 4-1 전체 상태 기본·모집중 필터·등록 최신순·10개 더보기 · 행사 관련 공고는 신규 표시 영역

왜 정하나요?

같은 행사 항목에 연결된 공고를 보여주기로 했지만 모집 중만 볼지, 마감·완료도 함께 볼지는 정하지 않았습니다. 일반 공고 목록은 전체 상태·등록 최신순이 기준입니다.

예시로 보면

관련 공고30개 중 대부분이 마감됐을 때 처음 무엇이 보이는지의 차이입니다.

함께 알아둘 점

삭제·차단·신고 숨김·비로그인 개인정보 보호 등 기존 조회 권한은 모든 안에 유지합니다. 모집 중이라는 표시가 특정 회원의 신청 가능을 무조건 보장하지는 않습니다.

E08 · 선택 필요

비로그인에서 동행 구하기를 누른 뒤 어디로 돌아올까요?

대조 근거: 정책 공개 행사 열람·가입 조건 · 현재 RemoteEventDetail의 로그인 이동에서 행사 문맥 전달 부족

왜 정하나요?

행사 정보는 비로그인도 볼 수 있지만 공고 작성은 로그인이 필요합니다. 로그인하면서 고른 행사를 잃어버리지 않도록 복귀 위치를 정해야 합니다.

예시로 보면

로그인하지 않은 사람이 뮤지컬 상세에서 이 행사로 동행 구하기를 누른 뒤 네이버 가입을 완료한 상황입니다.

함께 알아둘 점

가입 조건 미충족·로그인 취소 상태에서 작성 완료를 허용하지 않습니다. 복귀 정보는 행사 식별자 등 필요한 최소 정보만 사용하며 상세 주소·개인정보 공개 권한을 바꾸지 않습니다.

E09 · 선택 필요

직접 입력 행사의 주소는 어떤 방법으로 받을까요?

대조 근거: 최신 대화의 직접 입력 공개 행사장 주소 허용 · 정책의 동행 상세 만남 지점 보호·등록 전 개인정보 검사

왜 정하나요?

행사명 필수·장소명과 공개 행사장 주소 선택은 이미 정했습니다. 남은 것은 주소 입력 방법입니다. 검색으로 선택하더라도 개인 집 주소 입력을 완전히 막는다고 보장할 수는 없습니다.

예시로 보면

공개된 공방 주소는 적을 수 있어야 하지만 개인 집 동호수를 행사 주소 칸에 공개하면 안 됩니다.

함께 알아둘 점

API의 공개 행사장 주소와 공고의 비공개 만남 지점은 별도입니다. A/B의 공개 주소는 공고 상세 행사 영역에 표시하고 공고 목록의 동까지 공개 기준은 유지합니다. 입력 검사만으로 주소의 공개성·안전성을 완벽히 판정했다고 표현하지 않습니다.

E10 · 선택 필요

신청자가 생긴 뒤 연결 행사를 바꾸거나 삭제하면요?

대조 근거: 정책 4-3 확정 전 핵심 조건 변경 알림·최종 동의 무효화 · 확정 후 약속 조건 변경 합의 흐름

왜 정하나요?

버튼 삭제는 행사 자체가 아니라 연결만 없애는 동작으로 정했습니다. 그러나 이미 상대가 그 행사를 보고 신청했거나 확정한 뒤라면 단순 장식 수정과 다르게 다뤄야 합니다.

예시로 보면

뮤지컬 동행으로 확정한 뒤 작성자가 연결 행사를 영화로 바꾸거나 직접 입력 행사명을 전혀 다른 활동으로 바꾸는 상황입니다.

함께 알아둘 점

원천 기관의 자동 정보 갱신은 작성자의 행사 교체와 다릅니다. API 정보 갱신만으로 약속 조건·일정을 자동 변경하거나 상대가 동의했다고 처리하지 않습니다. 오탈자 등 비실질 변경 분류는 구현 때 기존 변경 계약과 맞춥니다.

E11 · 선택 필요

연결 행사 취소·연기를 발견하면 별도 알림도 보낼까요?

대조 근거: 최신 대화의 취소/연기 표시 확정 · 정책 알림 목록에는 원천 행사 상태 변경 전용 항목 없음

왜 정하나요?

카드·상세에 상태를 표시하는 것은 확정했습니다. 사용자가 화면을 다시 열지 않아도 알게 할지, 추가 알림까지 만들지는 미정입니다.

예시로 보면

축제 취소가 수집됐지만 확정 당사자가 행사 상세를 다시 보지 않아 아직 모르는 상황입니다.

함께 알아둘 점

끝난 동행의 과거 당사자나 단순 조회자 전원에게 보내는 안이 아닙니다. 정보 미제공·단순 조회 누락을 취소 알림으로 보내지 않습니다. 이는 앞으로 구현할 알림의 설계 선택이며 지금 외부 메시지를 보내는 승인이 아닙니다.

E12 · 선택 필요

비표출됐던 행사가 다시 표출되면요?

대조 근거: 최신 대화 비표출 A안·연결 유지 · TourAPI showflag와 최신 정보 재검증 필요

왜 정하나요?

비표출이면 안내 카드로 바꾸고 내부 연결은 보존하기로 했습니다. 이후 기관이 다시 공개했을 때 원래 카드를 자동 복원할지 정하지 않았습니다.

예시로 보면

어제는 비표출이었던 축제 정보가 오늘 정상 표출로 돌아왔고, 제목과 장소도 일부 수정돼 있습니다.

함께 알아둘 점

한 번 조회 성공만으로 표출 재개를 추정하지 않습니다. 기관의 표출 상태와 필요한 공개 조건을 확인합니다. 취소·연기 상태가 남아 있으면 복원하더라도 해당 안내를 유지하고 연결 가능으로 바꾸지 않습니다.

답변 이후 진행

  1. 선택과 기타 의견이 서로 충돌하는지만 확인합니다. 새로운 충돌이 없으면 반복 승인 없이 문서 동기화를 진행합니다.
  2. 정책·요구사항·화면·흐름·계약·작업/인수인계 문서를 대조해 확정 정책을 맞춥니다. 과거 실제 검증 기록을 새 구현 완료로 바꾸지는 않습니다.
  3. 종현 담당 TASK와 UX/UI를 함께 진행합니다. 서버가 필요한 기능은 민규 인수인계와 구분하고, 먼저 만들 수 있는 화면·컴포넌트를 진행합니다.

미결정 제품 선택과 확인할 기술 사실은 별도입니다. 실제 원천 상태값·URL 이용조건·직접 입력 저장 계약·비표출 안전 응답·연결 공고 조회·알림 전달은 구현/검증 과제이며, 선택만으로 완료 처리하지 않습니다. 서울 HTTPS와 KOPIS 순위 집계기간 확인도 별도로 유지합니다.
