# J07 결과 기록 이후 취소·평가 기준 설계 — 2026-10-14

전체 **79%(22/28)** 유지. 종현 한시 수정·실제 검증·원복 묶음은 [완료 기록](2026-10-14-temporary-validation-result.md)의 범위로 보존한다. 이번 문서는 자동 계속 목표의 J01~J09 요구사항별 감사에서 새로 확인한 제품 해석 공백과 다음 설계다. 제품 코드·SQL·평가 허용 기준을 아직 바꾸지 않았다.

## 현재 관찰과 기존 예외

`ai-chat/handler.ts`는 정상3종 결과의 최종 개인정보 검사를 끝내고 record 포트를 호출한 뒤 요청 점유를 finish한다. 기록 대기 중 취소/타임아웃/응답 유실이면 HTTP 실패로 끝나지만, finally가 기존 outcome 기본값 `finished`로 점유를 정리할 수 있다. 현재 DB 평가 조건은 같은 본인의 결과 receipt와 `ai_chat_requests.outcome='finished'`다.

기존 [AI 계약](../../../../backend/contracts/ai-chat.md)은 결과 증거를 **서버가 응답을 제공할 준비가 된 시각**으로 정의한다. 화면 표시·열람·유용함 증거가 아니며, 기록 RPC 시작 뒤 취소/응답 유실이면 원 기록을 보존할 수 있다고 명시한다. 따라서 receipt가 남거나 HTTP가 실패했다는 사실만으로 새 구현 결함으로 단정하지 않는다. 아직 명확하지 않은 것은 **이 예외가 helpful 접수 허용까지 포함하는지**다.

| 재현 조건 | 현재 handler HTTP | 모형 DB 상태 | 같은 요청 helpful 모형 |
|---|---|---|---|
| 기록 처리 중 사용자 취소 | 500 | receipt 존재·finished | accepted |
| 기록 효과 이후 응답 유실 | 500 | receipt 존재·finished | accepted |
| 기록 대기 중 DB 점유 만료 | 500 | receipt 존재·outcome 미완료 | 거절 |

이것은 실제 handler·feedback 포트와 상태를 유지하는 RPC 모형을 연결한 재현이다. 실제 Auth·DB·공급사·Storage 호출은0이다. DB 실행 성공이나 실제 회원의 평가 접수로 확대하지 않는다. 사용자 취소·기록 응답 유실 두 사례는 lease가 유효하다는 전제다. native SQL은 DB 점유 만료 뒤 finish를 거절하고 outcome이 미완료인 helpful도 거절한다. 첫 모형의 만료 검사가 빠져 이 세 번째 사례를 과대 재현했으므로, v2에 실제 SQL의 만료 조건을 반영해 거절로 정정했다. v1 원 증거는 보존한다. 모형의 로컬 시각은 실제 DB clock/경합 검증이 아니다. 재현의 최초 feedback 인자형 오류는 모형 호출을 올바른 userId로 고쳐 해결했으며 제품 코드 수정은 없었다.

- 재현 source HEAD: `91c0c6973a09d7638f7a9b296dbc0c3030f37120`.
- 비공개 원 증거: `/private/tmp/yumidang-jonghyun-20261014-result-cancellation-reproduction-v2.json`.
- 증거 SHA256: `60aab2e602ec68d2ddd521e5a0337a6c7e41d134f4d6a4e394669086550d9d06`.
- 실제 source SHA와 재현 핀4개 일치 확인. 새 상태 검사로 기존257개 또는 실제 f267 실행을 다시 PASS로 표시하지 않는다.

## 설계 대안 — 선택 전 구현하지 않음

1. **기존 결과 준비 의미 유지와 원 요청 상태 GET 확인:** DB에서 같은 본인의 정상 결과 확정이 확인되면 post-record 취소/응답 유실 뒤에도 helpful을 허용한다. GET은 결과 준비/처리 상태만 읽고 모델·차감·기록·finish를 다시 호출하지 않는다. 대화 원문/답변 본문을 서버에 저장하지 않으므로 답변 재생 기능은 아니다. 기존 기록과 UNKNOWN을 삭제하지 않는다.
2. **취소된 요청의 새 helpful 차단:** 원 기록과 원 예산은 보존하면서 평가 가능 상태를 정상 확정과 분리한다. 단순 기록 삭제나 record/finish 순서 교체로 해결하지 않는다. 원자 DB 완료 RPC 신설 또는 기존 record RPC 원자화, 실패 정리와 성공 확정의 typed 구분, submit 조건·이전 caller·유실 복구를 함께 설계해야 한다.

어느 안이든 HTTP 취소와 DB commit은 같은 원자 작업이 아니다. DB 확정 이후 응답 유실을 미전송/실패 확정으로 바꾸거나 자동 재전송하지 않는다. 새 정책은 사용자 선택 뒤 적용하며, 단일·다중 계정의 **미전송 확인 때만 요청 전체 자동1회** 결정은 다시 묻지 않는다.

## 동의 철회 후 기존 helpful

정책9는 해당 AI의 신규 전송 중단·관련 요약 숨김/필요 자료 삭제를 정한다. helpful은 모델 전송을 하지 않으며 현재 submit SQL은 활성 회원·본인 receipt·finished·90일 등을 검사하고 exploration_allowed를 helpful 조건으로 검사하지 않는다. 그래서 현재 구현은 기존 결과의 새 helpful을 허용할 수 있다. 기존 `withdrawn` 모형404를 실제 철회 후 거절 증거나 확정 정책으로 취급하지 않는다.

철회 후 기존 접수의 보존·90일 파기와 **새 helpful 접수**는 별개다. 새 helpful도 막을지, 기존 답변에 대한 로컬 평가를 허용할지는 이번 마지막 일괄 질문에 포함한다. 신고 자료·외부 원문·법적 승인·실회원 HOLD의 기존 조건은 바꾸지 않는다.

## 구현 경로와 검증 경계

변경이 필요하면 기존 `ai-chat/handler.ts`·`index.ts`, `_shared/db/ai-feedback-client.ts`·`internal-client.ts`, `ai/providers/member-request.ts`, `apps/mobile/src/service.ts`, 종현 책임 시험과 새 migration의 가장 구체적인 소유권을 확인한 뒤 그 경로에서 후속 구현한다. 성호 화면은 편집하지 않는다. 새 migration을 추가하면 현재119파일과 번호120을 혼동하지 않고 새로운 실제 파일 집합/핀을 만든다.
