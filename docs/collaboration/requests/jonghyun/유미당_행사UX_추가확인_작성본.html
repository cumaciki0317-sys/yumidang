작성본에서 남은 충돌과
통합 기준 3개만 확인해요

범위는 행사 목록·상세·공고 연결·직접 입력과 그에 따른 오류·수정 흐름입니다. 앞선 12항목의 선택은 보존했습니다. 날짜 검색의 충돌과 통합의 실행 기준만 묻습니다.

각 항목은 A·B·C 세 안 + D 기타 직접 작성입니다. 추천안도 미리 선택하지 않았습니다. 예시는 설명을 위한 가상 상황입니다.

기타를 고르면 원하는 기준을 입력해 주세요. 추천안을 수정하고 싶으면 해당 안을 선택한 뒤 추가 의견을 적어도 됩니다. 답변이 완료된 뒤 정책·PRD·IA·USERFLOW·설계·계약·인수인계 등 관련 문서를 담당 구분 없이 동기화합니다. 지금 저장하는 것은 답변이며 구현·배포가 아닙니다.

같은 브라우저에는 자동 저장됩니다. 파일을 이동하거나 다른 도구에 전달하려면 ‘작성본 HTML 저장’을 사용하세요. 일부 브라우저에서 자동 저장이 안 되더라도 작성본 저장은 사용할 수 있습니다.

이미 확정한 내용 보기 — 다시 고르지 않습니다
  1. 일반 공고 작성에서는 행사 영역을 맨 아래, 행사 상세에서 동행 구하기로 진입한 작성에서는 맨 위에 둡니다.
  2. 행사 기간과 만남 일정의 겹침을 강제하지 않습니다. 날짜가 다르다는 이유만으로 연결·등록을 거절하지 않고 달력에 연결 행사의 진행 날짜를 색으로 표시합니다.
  3. 일반 목록의 이번 주 기본 유지, 검색은 실제 조회 가능한 전체 기간, 작성용 예정·진행 중 검색/목록과10개 더보기는 확정입니다. 자동 날짜 축소만 F01에서 정합니다.
  4. 실제 수신되는 TourAPI 타입15 전체를 포함합니다. 검증된 동일 행사는 대표 카드·상세·연결 공고 목록으로 통합합니다. 통합 자체를 다시 고르는 질문이 아닙니다.
  5. 등록 확인 실패 시 입력 보존·재시도/연결삭제, 취소 정보 미제공 구분, 연결 공고 전체 상태 최신순+모집중필터, 로그인 후 원행사 연결 작성 복귀를 적용합니다.
  6. 직접 입력 주소는 기존 장소/주소 검색+공개 확인, 실질 행사 변경은 핵심조건 변경, 취소·연기 관련 당사자 앱 안 알림, 확인된 표출 재개 시 최신 검증정보 복원을 적용합니다.
  7. 기존 카드·상세·공고전용 직접입력·비표출A 결정을 유지합니다. 직접 입력을 검수해 공용 행사로 만드는 작업은 추가하지 않습니다.
F01 · 선택 필요

만남 날짜에 맞춰 행사 검색을 자동으로 좁힐까요?

대조 근거: 사용자 작성본 E01 D 원문 vs E02 A 중 날짜 자동 축소 부분

왜 정하나요?

E01 직접 작성은 날짜를 강제하지 않고 달력에 행사 날짜만 색으로 알려주자는 내용입니다. E02 A에는 만남 일정이 있으면 겹치는 행사로 검색을 자동 축소한다는 문구가 남아 있습니다. 겹침 강제 제거는 이미 확정했고 검색 동작만 확인합니다.

예시로 보면

11월1일 공연을 위해 10월31일 사전 모임을 작성합니다. 10월31일에 열리는 행사만 자동 검색하면 11월1일 공연을 찾을 수 없습니다.

함께 알아둘 점

세 안 모두 행사 영역의 진입별 위치와 만남 일정 비강제는 유지합니다. 취소·종료·비표출 등 별도로 확정한 새 연결 제한은 날짜 겹침 검사와 다릅니다.

F02 · 선택 필요

같은 행사라고 검증하는 방법은 무엇으로 할까요?

대조 근거: 사용자 작성본 E04 B · 현재 provider+sourceId 개별 저장 계약에는 기관 간 동일성 기준/연결표가 없음

왜 정하나요?

E04 B의 검증된 동일 행사 통합은 확정입니다. 하지만 무엇을 검증으로 인정할지는 정해지지 않았습니다. 행사 이름·장소·기간이 비슷해도 축제 전체와 개별 프로그램 또는 다른 회차일 수 있습니다.

예시로 보면

가을음악축제 전체와 그 안의 가을음악축제 특별공연을 잘못 합치면 서로 다른 동행 공고가 한곳에 섞입니다.

함께 알아둘 점

A의 공식 공통 근거가 세 API에서 실제 확보됐는지는 미확인입니다. A를 고르면 초기 통합 건수가 적거나 없을 수 있습니다. 어떤 안도 단순 제목만으로 합치지 않고 원천 ID·기존 공고 관계·통합 근거와 되돌리기 기록을 보존합니다. C는 공고 직접입력을 공용화하는 검수가 아니라 API 행사끼리의 중복 검증이며, 그래도 별도 운영 비용이 생깁니다.

F03 · 선택 필요

통합한 행사의 대표 정보와 출처 충돌은 어떻게 처리할까요?

대조 근거: 사용자 E04 B 통합 + 기존 비표출 A/새 연결 제한/E12 복원 결정을 복수 원천에 적용할 때 필요한 기준

왜 정하나요?

한 행사로 묶어도 기관별 날짜·장소·취소·비표출 값이 다를 수 있습니다. 한 원천의 비표출을 전체 행사에 적용할지, 다른 공개 자료로 유지할지는 기존 비표출 A안만으로 정해지지 않습니다.

예시로 보면

TourAPI 자료만 비표출이고 서울 자료는 공개입니다. 또는 같은 행사에 대해 한 기관은 취소, 다른 기관은 예정이라고 제공합니다.

함께 알아둘 점

A/B는 대표 출처가 비표출이면 그 원천의 값을 재사용하지 않고 검증된 다른 공개 원천으로 전환합니다. 공개 원천이 하나도 없으면 기존 비표출 A 안내 카드가 됩니다. 일반 주간 행사와 KOPIS 공식 순위는 별개이므로 순위 집계나 순위 원천을 합치지 않습니다. 실제 상태값 확인·충돌 해소·재표출 검증은 서버 작업이며 선택만으로 완료되지 않습니다.

답변 이후 진행

  1. 선택과 기타 의견이 서로 충돌하는지만 확인합니다. 새로운 충돌이 없으면 반복 승인 없이 문서 동기화를 진행합니다.
  2. 정책·요구사항·화면·흐름·계약·작업/인수인계 문서를 대조해 확정 정책을 맞춥니다. 과거 실제 검증 기록을 새 구현 완료로 바꾸지는 않습니다.
  3. 종현 담당 TASK와 UX/UI를 함께 진행합니다. 서버가 필요한 기능은 민규 인수인계와 구분하고, 먼저 만들 수 있는 화면·컴포넌트를 진행합니다.

미결정 제품 선택과 확인할 기술 사실은 별도입니다. 실제 원천 상태값·URL 이용조건·직접 입력 저장 계약·비표출 안전 응답·연결 공고 조회·알림 전달은 구현/검증 과제이며, 선택만으로 완료 처리하지 않습니다. 서울 HTTPS와 KOPIS 순위 집계기간 확인도 별도로 유지합니다.
