# 민규에게 연결할 UX 서버 과제 — 2026-10-23

새 정책 선택 요청이 아니라 이미 확정한 동작을 실제 서버와 연결하기 위한 인계다. 이 문서 작성만으로 서버 구현·협의·운영 적용 완료로 보지 않는다.

1. **후기 AI 선택 동의 3종 독립 조회·변경(Q10)**: 요약 열람, 내 프로필 요약 생성·노출, 작성 후기 활용을 각각 읽고 철회할 수 있는 계약이 필요하다. 현재 `review_summary` 전체 철회 하나를 개별 철회로 소비하면 다른 동의까지 바뀌므로 연결하지 않았다. 기존 원문 활용 철회의 요약 숨김→적격 자료 재생성, 외부 사본 삭제 확인 경계는 정책 그대로다.
2. **행사에 연결된 공고 조회(Q12)**: 검증한 행사 ID와 공고 ID 관계를 기준으로 전체 상태·최근 등록순·모집 중 필터·10개 더보기를 조회해야 한다. 행사명 키워드 검색은 동명이거나 이름이 바뀐 행사에서 다른 공고를 섞으므로 대체하지 않는다. 미연결·실패는 0건이 아니다. 직접 입력 행사에는 공용 행사 ID·별도 상세를 만들지 않는다.
3. **후기 작성 불가의 추가 사유(Q07)**: 기존 계약에는 `disputed`, `released`, `own_review`가 이미 있다. 최신 SQL은 본인 후기를 `{experience,praises,rating,comment,submitted_at}`으로 반환하며 본인 후기 존재 시 `can_write=false`다. 앱이 `own_review`를 덜 소비한 누락을 이번에 보완했다. 유효한 본인 제출 기록이면 이미 작성했음을 안내하고 기존 약속 상태 확인·상태 재조회를 재사용한다. 분쟁은 우선 안내하며, 본인 제출과 상대 후기 공개를 혼동하거나 원문을 추가 노출하지 않는다. 이 사례는 새 사유 코드 대기가 아니다. **나머지** `can_write=false`의 확인되지 않은 사유만 공개 가능한 코드·다음 행동 계약의 후속이다. 그 전에는 마감·상대 완료 대기 등으로 추정하지 않는다.
4. **직접 입력 행사 실제 저장(Q06)**: 이름 필수·공개 장소/주소 선택, 해당 공고에만 표시하는 확정 정책과 기존 소비 준비를 유지한다. 민규의 실제 저장/검증 응답 연결 전 앱에서 실제 공고 등록 성공으로 표시하지 않는다.
5. **AI 이용 가능 상태 확인(기존 A 선택 유지)**: 중단 응답 뒤 안내·입력을 유지하고 자동 재전송하지 않는다. 서버 판단을 유지하며 상태 확인 수단을 먼저 맞춘 뒤 종현이 버튼 제어를 연결한다. 기기 횟수·자정 타이머·재진입만으로 사용 가능을 확정하지 않는다.

대표 운영자·대체자·동의 정책·KOPIS 기간은 이번 UI 변경으로 바꾸지 않았다. 실제 회원 데이터나 공급사 호출을 이 작업에서 새로 실행하지 않았다.

현재 제공 여부의 근거는 [요구사항별 최종 대조](final-requirement-audit.md)에 연결한다. 기존 `ai-chat`의 결과 상태 조회는 답변 평가 가능 상태이며, 새 요청의 한도·동의·동시 처리 이용 가능 상태를 대신하지 않는다. Android 실제 로그인은 앞선 앱 기반 작업에서 이미 native 인증 BE 연동 대기로 합의한 별도 과제다.
