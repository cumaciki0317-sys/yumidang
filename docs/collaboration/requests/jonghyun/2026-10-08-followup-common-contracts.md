# 종현 후속 연결: 민규 공통 포트 요청

2026-10-08, actor `jonghyun`. 사용자 승인 설계와 `40f3c1d`의 실제 공통 API를 기준으로 한다. 신규 RPC 이름은 임의 생성하지 않는다. 아래는 제공이 필요한 의미와 내부 포트이며, 운영 DB에 존재하는 계약을 뜻하지 않는다. 민규 코드·SQL·설정은 수정하지 않았다.

## 확정한 사용자 선택

- 실행기 공유 최대20은 처리 항목 수다. 취소·요약·행사·회원 정리는 작업 한 건, 신고는 첨부 파기와 메타데이터 정리를 각각 한 항목으로 센다. enqueue/claim/완료 RPC 호출 수와 처리 항목 수를 혼용하지 않는다.
- 정상 AI 결과·결과 없음·추가 질문 모두 helpful 대상이다. 오류·개인정보 차단·시간 초과는 제외한다. 서버의 응답 준비 기록은 실제 사용자 열람 증거가 아니다.
- helpful은 접수+90일 만료 예약으로 정리하고, 탈퇴 시 즉시 삭제한다. 매일00:01 일괄 정리로 대체하지 않는다. 장애 후 늦어진 정리는 원 만료 시각을 유지하고 복구 후 처리한다.
- 채팅은 실제 표시된 메시지 ID별로 읽음 처리한다. 본문 일부가 실제 화면에 나타난 경우도 포함한다. 마지막 위치 이전 전체를 읽음으로 간주하는 기존 watermark 경로로 대체하지 않는다.

## 실행기 원자적 처리 항목 배정

요청: 현재 전역 token이 유효한지 검증하고, 같은 실행의 원 최대20/180초 범위에서 항목을 원자적으로 예약하는 포트. 종현 내부 `reserveItem`과 RPC/Storage 호출 허가 `reserve`를 분리한다. 종현의 `allocate` 결과는 전달된 잔여 배정 이하로 제한한다.

항목 정체성은 취소 job/generation, 요약·행사·회원 정리의 기존 작업 키, 신고 job/task/closureProof 및 첨부·metadata 종류로 고정한다. 같은 실행·같은 항목의 재확인은 중복 차감하지 않으며 새 항목은 별도 예약한다. 전송 전 예약 실패 또는 예산0이면 새 처리를 시작하지 않는다. 응답 유실은 예약을 보존한다. RPC 호출 허가를 새20 한도나 종류별 새 전역 token으로 대체하지 않는다.

필요 반환: 현재 DB서버 시각, 유효 원 전역 token의 잔여 처리 항목·잔여 시간, 동일 항목 예약 여부. 요청 token·항목·세대가 불일치하거나 만료되면 거절한다. task 조회/점유와 항목 예약 사이 권한·fence를 같은 서버 계약에서 검증한다. 정확한 wire 이름은 민규의 후속 계약으로 제공한다.

회원 정리의 현재 while(succeeded<20) 고정 상한은 외부 배정 limit 이하로 조립할 수 있어야 한다. 종현이 민규 소비자를 수정하지 않는다.

## 자기 토큰 일정 조회와 영속 복구

기존 `read_worker_queue_schedule` ABI에는 자기 token 인자가 없다. 원 토큰이 현재 유효한 소유 토큰임을 검증한 경우에만 자기 점유로 발생하는 조회 지연을 제외하고, 다른 실행기의 점유는 존중하는 포트를 요청한다. 제외 종류/직전 종류 교대와 `{serverNow,nextDueAt,nextKind}`를 보존한다. 전역 점유 획득이 경쟁자로 거절되면 queue가 비어 있어도 완료증거/helpful 일정은 경쟁자 점유 만료 이후 재개할 미래 nextDueAt을 제공해야 한다. 과거 만료만 반환하면 즉시 재시도 금지 때문에 재개 timer가 없어질 수 있다. 새 DB clock·lease 연장은 하지 않는다.

scheduler/enqueue/claim/task/DELETE/ACK/settlement의 intent 저장, 원 intent 조회, 확정, unknown 전환과 재시작 조회가 필요하다. 외부 변경 전에 intent 저장을 확인한다. mutation 응답이 유실되면 원 intent를 보존하고 자동 재전송하지 않는다. 재접속·프로세스 재시작에서도 pending/unknown이 차단되어야 한다. 원 job/task/global/lease/fence/필요한 hash만 저장하며 키·원문·Storage 경로를 복제하지 않는다. 파일 시험 journal은 제품 포트가 아니다.

## 완료 증거·helpful 만료 예약

완료 증거의 기존30일 bounded purge와 helpful의 기존 `/internal/ai-feedback-maintenance` `{limit:1..100}`를 재사용한다. 두 자료의 저장 수명과 처리 범위를 혼용하지 않는다.

현재 helpful API는 내부 비밀만 확인하며 `x-worker-run-token`을 검증하지 않는다. 헤더 전달 자체가 fence가 아니다. 만료된 실행이 삭제를 수행하지 못하도록 내부 endpoint와 DB의 실제 token/잔여 배정 검증 계약을 제공해야 한다. 현 소비자 `scopedEndpointReady`는 그 계약 검증 전 false로 유지한다.

민규 제공 필요: 각 자료에 대해 `{serverNow,nextDueAt}` 조회, 접수·삭제·만료 변경 알림/예약 갱신, 내부 권한, 처리 intent·unknown 확인 계약. 서버 시각을 기준으로 timer를 설정하고 시작·재접속 때 다시 조회한다. batch 후 남은 만료 항목을 조회해 이어가며 빈 큐/같은 due 오류에 즉시 재시도 루프를 만들지 않는다. 새 cron/임의 폴링 주기는 만들지 않는다. 조회 실패·미확인 삭제 응답은 영속 상태 보존 후 복구로 넘긴다.

helpful은 만료 시각부터 새 접수를 거절하는 DB 조건과 실제 정리를 별도로 검증한다. 신고의 최종종결+90일 Storage 파기를 helpful 정리로 대체하지 않으며 reportReady=false를 유지한다.

## 실제 환경·인증 준비

현재 로컬 Docker daemon 접근 불가를 확인했다. 기존 민규 격리 DB 시험의 PASS를 이번 제품 실행기 검증으로 재사용하지 않는다. TLS CA·전용 LOGIN·HTTPS 함수 대상·LISTEN 권한과 승인된 격리 검증 환경을 민규가 제공한 뒤 두 runner 경쟁/연결유실/자동 재시작을 확인한다. production·Railway 재시작/배포는 수행하지 않는다.

웹 인증은 확인된 signup/supabase/publicKey/callback/origin 구성, native는 발급된 앱 등록·복귀 계약이 필요하다. 두 실제 네이버 적격 계정과 기기 준비도 별도다. 키·토큰·DB 비밀번호를 대화/인계에 요청하거나 기록하지 않는다.

## 후속 선택1A·2A·3A 확정: 메시지별 읽음 서버 확장

사용자가 개인정보 요청ID 분리, 실제 표시된 메시지별읽음/본문일부노출, 민규준비후통합을 모두 A로 확정했다. 새 질문으로 다시 승인받지 않는다.

민규 제공 필요: 인증회원 본인의 대화에 속하고 현재 열람가능한 message IDs만 읽음으로 기록하는 원자적 포트. 화면에 보이지 않은 과거 메시지는 위치가 이전이라는 이유로 읽음으로 바꾸지 않는다. 중복·동시요청은 멱등 처리하고, 삭제/다른대화/권한없음 ID와 불완전 목록은 조용히 성공으로 바꾸지 않는다. 처리결과는 확인된ID와 현재 서버 unread 개수를 반환하며 클라이언트시간·회원ID를 권한근거로 받지 않는다. 정확한 HTTP/RPC/wire는 민규가 제공한다. 종현의 typed 주입객체는 내부 소비자 계약이고 새로운 공개endpoint를 뜻하지 않는다.

종현 UI는 준비된 메시지별 포트가 설치된 경우에만 실제 본문이 보인 ID 집합을 전송한다. 미준비는 준비중 안내/전송0이며 기존 watermark API로 fallback하지 않는다. 긴메시지는 본문노출로 판정하며 카드패딩/날짜만 보인 경우와 구분한다. 스크롤해 과거가 새로 보이면 해당ID도 별도전송하고 미노출ID는 추가하지 않는다. 세션/대화방/포트 변경 뒤 늦은응답은 폐기한다.

기존 last_read_message_id/read_at 및 unread_count 조회의 이전클라이언트 호환/새 메시지별집계는 민규가 같은정식DB계약에서 정리한다. 위치기반RPC는 새 UI에 재사용하지 않으며 기존DB를 임의수정하지 않는다. 인계·격리환경 준비 뒤 unseen과거 보존, 긴본문/새로보인과거, 중복/역순/경쟁/권한거절을 실제로 검증한다.

최종 개인정보검사에서 서버 생성 result.requestId만 별도형식·문맥일치 검사후 분리한다. 사용자 clientRequestId/원문/모델문장 또는 다른식별자를 일괄허용하는 변경이 아니다. 공급사원문/AI신고 등 기존보류를 해제하지 않는다.
