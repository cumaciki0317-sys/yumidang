## 처리 순서와 이해가 필요한 차이

다음은 새 사용자 결정으로 확정한 값이 아니다. 의미가 불명확한 원천 상태·권리·확장 범위는 아래처럼 근거 확인 과제로 남기며 미확인 값을 임의 보정하지 않는다.

### G01 취소·연기와 기간 상태를 분리

- 담당/영향: 민규 / 목록/상세/새 동행 연결
- 확인: TourAPI progresstype는 명세에 있으나 현재 버리고 active 고정. 서울은 명시 상태 없음. KOPIS 공연예정/중/완료도 취소와 다름.
- 다음: 원천 실제값·코드·상태 의미를 확인해 계약 결정. unknown을 정상으로 추정하지 않음.
- 경계: 공급사 의미·서버 계약 확인 필요; 이번에 정책을 새로 확정하지 않음

### G02 포스터 URL의 공급사별 안전 규칙

- 담당/영향: 민규 → 종현 / 목록/상세 이미지
- 확인: KOPIS HTTP는 null. 서울 HTTPS query 이미지가 KOPIS 전용 SourceEventRecord 및 query 금지 DTO에 거절. TourAPI 현재 미수집.
- 다음: 고정 공급사 호스트/경로/허용 query/권리를 검토해 서버·DB·DTO를 함께 맞춘 뒤 화면 연결.
- 경계: 임의 HTTPS 치환·검증 규칙 완화 없음

### G03 설명·운영 안내의 개행/HTML

- 담당/영향: 민규 → 종현 / 상세 본문
- 확인: KOPIS 실제 sty 개행, 서울 제목/설명 꺾쇠·제어문자, Tour 선택 본문에 HTML/제어문자가 포함되면 현재 optionalPlain에서 제외(코드 확인, 실제 원본 미관찰).
- 다음: 원문 보존과 안전한 표시용 텍스트 변환을 설계. 해당 행 실패와 선택 정보 제외를 구분.
- 경계: HTML 직접 삽입·임의 내용 요약/삭제 없음

### G04 장소명과 주소의 의미를 맞춤

- 담당/영향: 민규 / 목록/상세/작성 장소 후보
- 확인: Tour 목록 addr2는 상세주소인데 placeName에 사용. KOPIS 시설주소 join 없음. 서울 실제 주소 없음.
- 다음: eventplace/시설 ID 조인과 원천 없는 주소 null 유지. 상세 만남 지점과 분리.
- 경계: 주소 추정·좌표 역지오코딩 새 API 도입 없음

### G05 원천 등록/수정/수집 시각 구분

- 담당/영향: 민규·종현 / 수집 갱신·출처 표시
- 확인: KOPIS updatedate/등록일, Tour modifiedtime/createdtime, 서울 rgstdate=신청일은 서로 다름.
- 다음: collectedAt은 우리 수집 시각만. sourceUpdatedAt 확장 후보와 원천값 분리.
- 경계: 이번 주 신규는 기존 행사 시작일 기준 유지; 등록일 기준으로 바꾸지 않음

### G06 TourAPI 새 지역·분류 체계

- 담당/영향: 민규 → 종현 / 지역/분류 필터
- 확인: 공식 Swagger가 areaCode2/categoryCode2 등 구체계를 미사용·삭제예정으로 표시. ldong/lclsSystm 제공.
- 다음: 공식 코드/표시명·실제 응답 확인 후 기존 저장 데이터와 호환 계획.
- 경계: 코드 문자열을 UI 이름으로 바로 노출하거나 타 공급사 장르와 자동 동치 처리하지 않음

### G07 행사 상세의 관련 공고 목록

- 담당/영향: 민규 → 종현 / 행사 → 동행 탐색
- 확인: 외부 API에 유미당 공고는 없음. 현재 RemoteEventDetail은 관련 공고 목록을 표시하지 않음.
- 다음: 내부 eventId 관계·현재 공고 공개 권한을 지키는 조회와 빈 결과/조회 실패 상태 연결.
- 경계: 임의 행사명 검색으로 관계를 만들어내지 않음

### G08 부가 정보 확장 범위

- 담당/영향: 종현 설계 → 민규 계약 / 상세 보조 섹션
- 확인: 예매처·출연진·관람 연령·기관·문의·시설·좌표 등 원본은 있으나 공통 계약 없음.
- 다음: 필요한 섹션을 선택한 뒤 타입/수집/저장/공개/누락/권리 조건을 함께 확장.
- 경계: 확장 후보를 승인·구현 완료로 표시하지 않음

### G09 독립 진행과 기존 담당 유지

- 담당/영향: 민규 7.9/7.12, 종현 2.8/3.8 / 작업 순서
- 확인: 서울 HTTPS는 민규 인계. KOPIS 순위 집계는 Dots 대조 결과 후 판단. 이번은 데이터·화면 매핑.
- 다음: 일반 기능 개발/다른 API 정리는 병행. 즉시 추가 호출/주기 폴링 지시 아님.
- 경계: 노션 수정·운영·서버 구현·배포 없음

## 누락·실패 표시 원칙

- 제목/ID/기간 등 핵심값 손상과 선택 부가 정보 결측을 분리한다. 선택값이 없다고 가짜 내용을 채우지 않는다.
- 입장료 미확인·주소/장소 미확인·포스터 없음은 각각 다르다. “무료 1:1 동행”으로 행사 유료 입장료를 가리지 않는다.
- 수집 미연결/오류를 “행사 0건”으로 표시하지 않는다. 관련 공고 0건도 API 미연결/오류와 구분한다.
- sourceStatus는 취소 등 원천 상태, state는 기간상 상태다. sourceUpdatedAt은 원천 수정일, collectedAt은 우리 수집일, 순위 집계 기간은 별도다.
- 동일 provider+sourceId만 식별한다. KOPIS/관광공사/서울에 같은 행사가 있어 보여도 제목·장소만으로 자동 합치지 않는다.
- 장소/행사안내/이미지 URL은 공개 원천 정보이며 회원 상세 만남 지점과 섞지 않는다. 임의 원격 fetch/HTTP→HTTPS 일괄 치환/HTML 직접 삽입은 하지 않는다.

## 화면 작업과 서버 작업 순서

1. 이번 산출물을 기준으로 기본 카드/상세/연결 행사 표시 항목과 결측 문구를 검토한다. 기존 데이터 모델을 새로 만들지 않는다.
2. 현재 공통 계약의 제목·기간·장소·입장료·설명·운영·출처부터 화면을 다듬는다. 현재 API가 주지 않는 확장 후보는 숨기거나 설계상 대기로 구분한다.
3. 민규는 G01~G08의 수집/정규화/저장/공개 계약 차이를 기존 경로에서 해결한다. 서울 HTTPS7.9/일일수집7.12와 KOPIS 순위 검증은 별개로 유지한다.
4. 계약이 준비된 범위부터 종현3.8에서 실제 서버→앱 목록/상세/작성연결·실패·취소/종료를 검증한다. 이번 매핑 작업을3.8완료로 집계하지 않는다.
