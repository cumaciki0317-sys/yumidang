# 시간 처리와 요약 등록·실행 분리 요청

2026-09-29 · 요청 작성자 jonghyun · 대상 주담당 minkyu · 사용자 Q2 선택 반영

## 범위와 현재 상태

사용자가 시간 처리와 요약 처리를 분리하도록 설계를 선택했고, 이번 구현에서는 요청 명세를 인계하도록 승인했다. 실제 SQL·공통 설정·maintenance·scheduled-jobs 코드는 이번 검색 작업에서 변경하지 않았다. 외부 전송·DB 실행·Cron 등록도 하지 않았다.

현재 민규 [maintenance](../../../../backend/supabase/functions/service-api/routes.ts)는 요약 버전이 없으면 자동 완료 호출 전 실패한다. [후기 자동화 SQL](../../../../backend/supabase/migrations/20260923101000_review_automation.sql)은 버전 검사·후기 공개·outbox 소비·작업 등록을 한 트랜잭션에서 수행한다. 종현 [예약 bridge](../../../../backend/supabase/functions/scheduled-jobs/index.ts)에도 모델 선행 검사가 있고 통합 집계 응답만 받는다. [공통 환경](../../../../backend/supabase/functions/_shared/config/env.ts)은 모델 값이 누락된 경우와 빈 문자열로 잘못 지정된 경우의 처리가 다르다. HTTP 검사 순서만 바꾸면 이 결합이 모두 해소되지 않는다.

## 사용자 확정 동작 요구

| 상황 | 시간 처리 | 요약 등록·실행 |
|---|---|---|
| 모델/프롬프트 미확정·누락 | 공통 인증·DB와 기존 시간/상태 조건을 충족하면 자동 완료·적격 후기 공개 진행 | 설정 대기로 구분하고 호출하지 않음. outbox 보존 |
| 모델 전용 설정 오류 | 시간 처리의 시작까지 막지 않음 | 해당 경로만 구성 오류. 가짜/기본 버전 금지 |
| 명시 설정 준비 | 기존 시간 정책 유지 | 처리 시점 최신 snapshot/revision을 확인해 작업 등록 |
| 공급사 장애·예산/보관 조건 미충족 | 시간 처리와 독립 | 모델 활성화 경계 유지. 버전 문자열만으로 실제 모델 호출을 승인하지 않음 |

내부 인증과 공통 DB 설정은 계속 필수다. 수동 완료의 양쪽 확인, 자동 완료 예외, 지연 시 실제 처리 시각, 알림 가능 시점 +24시간과 완료부터 7일을 유지한다. 후기 공개는 기존 policy 후보·적격성만 판단하며 override 숨김을 재공개하거나 과거 후기를 일괄 공개하지 않는다.

## 유실·중복 없는 처리

1. 시간 경로는 outbox를 처리 완료하거나 삭제하지 않는다. 대기 중 여러 변경은 기존 profile별 최신 필요 상태로 합치며 원문·가짜 버전을 추가하지 않는다.
2. 원문·공개·관계 변경 시 revision 증가·기존 요약 무효화·outbox 기록을 같은 트랜잭션에 유지한다. checkpoint 확장 시 관련 중간 저장 삭제도 함께 보장한다.
3. 요약 등록 경로는 최신 공개 텍스트 후기 3개 이상일 때 현재 문자열 revision과 명시 버전으로 등록한다. 현재 3개 미만이면 작업 없이 해당 필요 기록을 해소한다. 모델 설정 대기 중 시간 경로가 이를 대신 소비하지 않는다.
4. 최신 snapshot 확인·중복 없는 enqueue·해당 outbox 제거는 원자 처리한다. enqueue 실패 시 기록을 보존하며 처리 도중 더 최신 변경도 오래된 소비로 잃지 않는다.
5. profile/revision/modelVersion/promptVersion의 기존 중복 키를 재사용한다. 재호출로 작업·게시·완료 알림이 중복되지 않게 한다. 모델 버전 변경만으로 전체 profile 재등록을 추가하지 않는다.

## 실패·응답 계약

- 자동 완료 성공 뒤 후기 공개가 실패해도 완료 상태·시각·알림은 유지한다. 재호출은 완료를 중복 처리하지 않고 남은 공개 처리를 회복할 수 있어야 한다.
- 공개 트랜잭션 실패는 공개·revision·outbox 변경을 함께 롤백한다. 요약 등록 실패는 작업 생성·outbox 삭제를 함께 롤백하며 별도로 성공한 시간 처리를 실패로 바꾸지 않는다.
- 성공, 정상 0건, 설정 대기, 실패, 앞 단계 성공 후 다음 단계 실패를 구분한다. 대기를 enqueuedCount=0만으로 숨기거나 실패를 빈 성공으로 바꾸지 않는다.
- 작업 등록과 모델 생성·게시 완료는 다르다. 원문·자격증명·SQL 상세 오류를 응답/로그에 넣지 않는다.

## 기술 제안과 파일별 책임

시간 처리 연산과 요약 outbox 소비 연산을 독립 호출 가능한 DB/RPC 경계로 나누는 안을 제안한다. 공통 API/RPC 명칭은 민규가 계약에 반영하되 위 동작 의미를 유지한다. 시간 경로는 기존 자동 완료 다음 공개 전용 연산, 요약 등록은 별도 트랜잭션으로 구성한다. 약속 → projection → outbox의 잠금 순서를 유지하고 outbox 소비에서도 projection을 먼저 잠근다.

- 민규: 후속 migration·권한·RPC 허용 목록·공통 환경·service-api 및 민규 검사.
- 종현: 확정된 새 계약 수령 후 별도 하네스에서 scheduled bridge의 모델 선행 차단·응답 투영·관련 검사를 수정.
- 미정 유지: 운영 주기·배치·lease·재시도·동시 실행값, 모델·예산·보관·품질 기준. 테스트값을 운영 기본값으로 채우지 않음.

요약 DB의 현재 점유/만료 검사·checkpoint 저장/게시와 원자 삭제·failedAttempts와 정상 재개 구분·failed/superseded 종결 보장은 [9/28 인계](2026-09-28-connection-handoff.md)의 별도 선행 요구다. 순차 RPC나 claim 횟수의 이름 변경으로 대신하지 않는다.

## 후속 구현의 인수 검사 — 이번 NOT_RUN

| 묶음 | 확인할 실제 동작 |
|---|---|
| 모델 미설정·오류 | 시간 처리 성공, outbox 유지, 요약 작업 없음. 인증 실패는 계속 차단 |
| 대기 후 재개 | 대기 중 변경된 최신 revision만 등록. 3개 미만이면 작업 없음 |
| 실패·재호출 | 완료 시각/알림 불변, enqueue 실패 시 outbox 보존, 재호출 중복 없음 |
| 경쟁 | 변경과 소비 동시 실행 시 최신 요청 유실/오래된 게시 없음, 잠금 순서 확인 |
| HTTP/bridge | 정상 0건·설정 대기·실패 구분, 최소 집계 필드만 반환 |

이 표는 요구와 인수 기준이며 실행 성공 기록이 아니다. 첫 검색 작업과 병렬로 민규가 검토할 수 있지만 종현이 민규 파일을 직접 바꾸지 않는다.
