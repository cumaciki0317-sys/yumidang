# 포텐스닷 계정 전환: 종현 준비 구현과 민규 연결 요청

기준: `jonghyun/queue-integration`, 사용자 최신 답변과 `정책.md`. 사용자가 팀원 계정 사용 동의를 확보했다고 알리고 구현·민규 인계를 승인했다. 팀원 동의는 공급사 공동 사용 허용 확인 또는 실제 회원 원문 전송 승인과 구분한다. 외부 메시지는 보내지 않고 이 문서로 인계한다.

## 현재 승인 범위와 진행 상태

종현은 여러 계정을 선택하는 모델 포트와 예약·정산·미확인 사용량 보존 구조를 준비했다. 사용자는 실제 키 등록·운영 연결 진행을 요청했다. 사용자 답변1A·2A로 유미 → 종현 → 민규 → 성호 순서와 로컬 서버 우선 연결·검증 후 운영 적용을 확정했다. 등록할 네 계정과 순서는 확정됐으며, 민규 공통 설정·DB/RPC 구현이 없어 실제 키·운영 `.env`는 아직 변경하지 않았다. 민규 담당 경로는 직접 수정하지 않는다. 숫자 예산과 계정 목록·순서는 외부 설정/원장 입력으로 받으며 기본320만이나 계정 예시를 코드에 고정하지 않는다.

사용자 답변③A로 계정당 한국시간 하루320만 토큰과 전체 예산=등록 계정별 상한 합계를 확정했다. 사용자가 유미·종현·민규·성호 네 계정을 이 순서로 지정했으므로 네 계정을 모두 등록하면 전체 한국시간 일일 상한은1,280만 토큰이다. 이는 서비스 운영 상한이며 공급사 포함량 또는 매일 확보되는 실사용량을 보장하지 않는다. 이 확정값을 민규 공통 설정·계정별/전체 원장에 반영해야 하며 기존 전체50% 제한을 함께 남겨 새 상한을 막지 않도록 연결한다. 운영 활성화는 미완료다.

## 종현 구현의 경계

- 계정 순서와 계정별 모델을 외부에서 제공받는다. 비밀 키를 반환 DTO나 로그에 넣지 않는다.
- 모델 전송 전 계정별 예산을 원자적으로 예약한다. 계정 예산 부족 때만 다음 계정 선택이 가능하며 전체 예산 부족이면 중단한다.
- 예약된 계정·예약ID·원장 일자에 호출과 정산을 고정한다. 요청 도중 임의로 다른 계정으로 재전송하지 않는다.
- 실제 보고 토큰이 없거나 시간 초과·응답 유실이면 예약을0으로 정산하거나 자동 반환하지 않는다.
- 일반403·429를 모두 소진으로 판단하지 않는다. 인증/권한·순간 요청 제한·일일 소진의 공식 기계 판정 기준이 필요하다.
- 한국시간 날짜 변경으로 미정산 예약을 지우거나 새 계정의 사용량으로 옮기지 않는다.

## 민규에게 필요한 공통 연결

| 대상 | 요청 | 완료 조건 |
|---|---|---|
| 공통 공급사 설정 | 등록 계정ID·사용 순서·각 서버 비밀 키 읽기와 검증, 단일키 설정과의 호환/우선순위 명시 | 중복/누락/잘못된 계정 설정은 거부하고 키값을 응답·로그에 노출하지 않음 |
| 계정별 원장/RPC | 공급사 계정ID·원장 일자·예약ID별 원자 예약과 정산·미확인 상태 유지 | 여러 작업자가 동시에 마지막 예산을 가져가지 않으며 일자 변경 뒤 늦은 정산도 원래 예약에 반영 |
| 전체 서비스 예산 | 사용자 결정에 따른 전체 예산과 계정별 예산을 함께 검사 | 전체 예산 소진은 계정만 바꿔 우회하지 않음 |
| 회원 하루20회 | 기존 회원 요청 게이트와 공급사 모델 호출 예약을 분리 | 여러 내부 호출·계정 선택 때문에 회원 요청 횟수를 중복 차감하지 않음 |
| 허용목록/권한 | 내부 서버만 예약·정산 RPC 호출, 계정 상태와 최소 식별값만 노출 | 클라이언트에 API 키·다른 회원 정보·원문을 반환하지 않음 |

환경변수 형식은 기존 [민규 연결 요청](2026-10-05-current-connection-requests.md)의 제안을 참고한다. `.env.example`·공통 설정·SQL·마이그레이션은 민규가 담당한다. 실제 등록 목록·순서는 사용자 답변에 따라`yumi,jonghyun,minkyu,sungho`로 확정했다. 변수명 형식은 민규 공통 설정에서 지원해야 하며 아직 실제 키는 등록하지 않았다. 로컬 서버에서 먼저 연결·검증하고 운영 서버에 적용한다.

## 실제 연결 전 확인

1. 사용자가 선택한 계정별·전체 예산 관계 반영.
2. 민규 원자 예약·정산·계정 설정 연결 후 종현 런타임 연결.
3. 기존 개인정보·보관 승인·공식 출력 상한 검사를 유지한 통합 검증.
4. 합성 요청으로 계정 선택·동시성·부분 실패·응답 유실·전체 소진·한국시간 자정 경계 확인.
5. 회원 요청당 총 토큰과 내부 호출 수를 측정해 회원20회 재검토.

실제 DB 동시성, 실제 공급사 다중 계정 호출, 키 등록, 회원 원문 전송, 운영 배포는 아직 미실행이다. 준비 코드의 단위 검사 통과를 이 검증의 완료로 보고하지 않는다.

## 확정된 정책 선택과 연결 과제

- 사용자 답변①A: 신고 자료는 최종 종결 후90일에 삭제하되 본인 선택 숨김은 본인이 해제할 때까지 유지한다. 최소 식별 기록을 자료와 분리하며 설명·캡처·증거를 남기지 않는다. 민규의 실제 숨김·해제 연결 전 선택 제공 보류는 유지한다. 차단·운영 제재와 별도다.
- 사용자 답변②A: 판정·사유·이의 방법을 앱에서 확인 가능하게 성공 제공한 서버 시각부터7일. 제공 실패 때는 기산하지 않고 최초 열람·외부 발송 시각과 구분한다. 일반 신고 결과 전체로 이의권을 확대하지 않는다. 민규는 안내 제공 시각과 마감의 서버 계약을 연결해야 한다.
- 사용자 답변③A: 계정별320만, 전체=등록 계정별 상한 합계로 확정. 실제 설정·원장 적용은 미완료.

## 구현·검증 결과

구현 파일: `backend/supabase/functions/_shared/ai/providers/account-pool.ts`.
검사 파일: `tests/functions/jonghyun/ai-account-pool.test.ts`.

`createAccountPoolModel({ orderedAccountIds, reservations, modelForAccount, confirmedDepletion? })`가 모델 포트를 만든다. 실제 계정 목록/순서는 서버 설정으로 받는다. 개인정보·보관·출력 제한 검토가 끝난 공급사 모델만 팩토리에서 전달해야 한다.

예약 포트는 `reserve({ accountId, task, inputBytes, maxOutputTokens, memberRequest? | summaryRequest? })`이며 다음 상태 중 하나를 반환한다.

- `reserved`: `reservation: { accountId, reservationId, accountDay }`.
- `account_budget_denied`: 모델 전송 없이 다음 계정 검사 가능.
- `global_budget_denied`: 계정을 바꾸지 않고 전체 예산 소진 처리.

정산 포트는 `settle({ reservation, outcome, usage?, confirmedDepletion? })`다. `outcome`은 `usage_reported` 또는 `usage_unknown`이며 실제 보고 사용량은 입력/출력 토큰이다. 계정·예약·원장 일자를 고정해 정산하고 미확인 건은 자동 환불하지 않는다. 회원 요청에는 `userId/requestId/leaseToken`, 요약에는 기존 작업 범위 식별자가 필수다. 범위와 근거 ID 배열을 복사·고정해 예약/모델 호출에 동일하게 전달한다. 이것은 회원 인증을 대신하지 않으며 DB에서 서버 범위와 현재 자격을 검증해야 한다.

민규는 전송 전 예약에서 기존과 같이 입력바이트·공급사 프롬프트 추가분·검증된 출력 상한을 고려해야 한다. 기술 예약 단위와 실제 공급사 토큰을 혼동하지 않는다. 정산은 멱등이어야 하고 예약/응답/정산 소실은 임의 재실행으로 해결하지 않는다.

현재 구조는 직접 예약 포트를 호출한다. 기존 `createModelRouter`로 다시 감싸면 이중 예약할 수 있어 운영 런타임 조립에서 중복을 제거해야 한다. 기존 자동1회 재시도 정책을 우회하거나 무제한 추가하지 않는다. 승인된 일일 소진 분류기가 연결돼도 현재 요청을 다른 계정으로 자동 재전송하지 않고 확인 근거만 정산에 붙인다.

검증: Node 단위 검사14개 PASS·Deno 타입 검사 PASS·소유권 검사 PASS. 전송 전/후 취소, 시간 초과/403/429, 미확인/상한 초과 사용량, 늦은 응답과 날짜 변경, 정산 실패, 요청 범위 누락/변조를 검사했다. 검사 포트는 메모리 대체 구현이며 실제 DB 원자성의 증거가 아니다.

실제 운영 런타임은 연결하지 않았고 기존 개인정보·출력 상한 미확인 차단은 유지한다. 민규 공통 설정/DB/RPC 계약, 확정된 네 계정의 실제 키 등록, 로컬 서버 연결 검증, 실제 회원/공급사 통합 검증을 준비해야 한다. 예산 정책은 확정됐다. 실제 키 접근·원격 API 호출·운영 설정 변경0이다.
