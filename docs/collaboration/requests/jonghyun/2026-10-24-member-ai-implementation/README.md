## 인터페이스와 실패 처리

- 앱 `MemberService`에 `aiConsents`, `setAiConsent(kind, allowed)`, `aiAvailability`를 추가했다. 정확한 종류·boolean·응답 필드·상태/시각을 검증하며 서버 계약/DB/API는 변경하지 않았다.
- 가입은 `complete` 입력을 유지한다. 확인된 ready 이후 선택값을 별도 메모리 상태로 옮겨 동의를 저장한다. 일부 실패는 GET 재조회와 사용자 수동 재시도로 처리하며 일반 가입은 유지한다.
- 기기 저장에는 epoch·토큰을 직렬화하지 않는다. 복원 시 현재 검증 세션을 붙이고 읽기 완료 전 쓰기를 막는다. 소유자/저장 세대와 초안 revision으로 늦은 읽기·쓰기·등록 성공 후 정리를 분리한다.
- 삭제 실패 marker와 메모리 차단으로 이전 자료의 복원을 막고 해당 기기 정리만 재시도한다. 서버 등록 성공 뒤 정리가 실패해도 재게시하지 않는다.
- 동의 변경은 세션과 별도로 revision을 무효화한다. 변경 중 요약을 새로 읽지 않고, 이전 재확인 버튼/좌표 측정/네트워크 응답이 새 계정이나 새 권한에서 작동하지 못하게 한다.

## 미실행과 남은 입력

실회원 검증 HOLD, 실제 공급사/운영 서버, Android 실기기 재시작·인증, APK·스토어·배포는 NOT_RUN이다. 실제 환경에서 콘텐츠 검사가 활성이라면 기존 앱의 검사 티켓 소비와 맞춰야 한다. 서버 기본 비활성 계약을 임의로 켜거나 앱의 검사 요청을 추측 추가하지 않았다.

이번 구현에서 사용자가 새로 결정해야 할 정책 충돌은 발견하지 못했다. native의 정확한 앱 복귀·일회용 교환·세션 수명과 대상 환경은 [민규 인계 입력8종](native-handoff.md)에 남긴 선행 조건이다. 이전에 정한 대기 경계를 유지하며 이번 부분 구현으로 WBS 전체 완료·프로젝트 완료율을 올리지 않는다.

[Notion TASK별 인계 문안](notion-handoff.md). 새 문서와 코드가 아직 원격/main에 공유됐다고 표시하지 않는다. 자동 커밋·푸시·병합·배포를 하지 않았다.

최종 인계: Notion 2.7·3.6·3.7·5.4b·3.1·3.2b·3.9·2.9 본문에 구조화 기록을 추가하고8개 페이지를 다시 열어 정확1회 저장을 확인했다. [저장 확인](evidence/notion-readback.json) · [범위별 종료 대조](completion-audit.json). 상태·진행률·담당·일정은 바꾸지 않았다.
