# 운영값 보수 제안 — 민규·팀 검토용 (2026-09-30, 미확정)

사용자 결정 U6·U7: Claude가 **보수적인 제안값**을 만들고 민규·팀이 검토해 확정한다. 아래 값은 **제안일 뿐 확정이 아니다.** 코드는 모든 값을 기본값 없이 환경값으로만 받으며, 값이 없으면 해당 기능만 꺼진다. 실제 사용량 데이터가 없어 출시 후 조정이 필요하다. 팀이 확정한 최신값만 [정책.md의 후속 확인](../../../../정책.md#follow-ups)과 설정 계약에 반영한다. 정책.md에는 과거값·변경 이력을 덧붙이지 않는다.

**전제:** 추가 유료 지출 0원(계정 요금제 근거 확인 대기), 한 응답이 오래 걸리지 않을 것, Supabase Edge 함수 1회 실행 시간 한도(요금제별 상이 — **배포 요금제에서 공식 수치 재확인 필요**) 안에서 끝날 것.

## 이미 확정된 범위와 검토가 필요한 값

- 행사 갱신·후기 요약 작업 등록은 매일 00:01 Asia/Seoul이다. 자동 완료는 예상 종료+24시간 건별 예약이며 후기 공개 시각은 실제 완료 기준이다. 운영값 제안으로 시각을 바꾸지 않는다.
- 모델은 포텐스닷 LLM/Sonnet 5, 추가 지출 0원 근거 확인 후 합성 10회 평가다. 실제 회원 원문 전송은 보관 조건 검토·사용자 확인 전 보류한다.
- 요약 중간 결과에는 자동 TTL이 없다. 완료·폐기·원문 변경·실패 종결 정리와 한도 소진 시 보존을 유지한다.
- 행사 대상은 KOPIS·TourAPI다. 서울은 HTTPS 등 연결 조건과 연결 여부 모두 팀 검토다. 공식 Top 10은 전국 전체 공연 기본/뮤지컬 전환, 어제까지 최근 7일·매일 갱신이다.
- 다음 표의 수치·원장 교체/보존 방식은 미확정 후보다. 사용자별 한도, 목록 페이지 크기, AI/작업 한도, 원장 운영값은 팀 검토이며 20개·10개·월 50% 등을 확정값으로 사용하지 않는다.
- 반환 직전 최신 상태 확인·일부 결과·실패 처리 세부 방식도 팀 검토다. 운영값만 확정해서 화면 동작까지 승인된 것으로 처리하지 않는다.

## 1. AI 탐색 (`ai-chat`)

| 변수 | 제안 | 이유 |
|---|---|---|
| `AI_CHAT_MAX_MESSAGES` | 20 | 한 탐색의 주고받기 10번 정도. 넘으면 “조건 유지한 채 새 탐색” 안내 |
| `AI_CHAT_MAX_MESSAGE_CHARS` | 500 | 조건 설명에 충분, 긴 붙여넣기 방지 |
| `AI_CHAT_MAX_TOTAL_CHARS` | 4000 | 모델 입력을 작게 유지(비용·속도) |
| `AI_CHAT_MAX_OUTPUT_TOKENS` | 800 | 조건 해석 결과는 짧은 JSON |
| `AI_CHAT_SEARCH_PAGE_SIZE` | 20 | 기존 공고 검색 기본 페이지 크기와 같음 |
| `AI_CHAT_MAX_SEARCH_PAGES` | 3 | 한 요청에서 최대 60건만 훑음(느려지지 않게). 넘었을 때 일부 결과 처리 세부 정책은 팀 검토 |
| `AI_CHAT_RECHECK_MAX_PAGES` | 5 | 응답 직전 재확인은 탐색보다 조금 넉넉히(새 공고로 밀린 카드 찾기) |
| `AI_CHAT_MAX_RESULT_CARDS` | 10 | 화면 한 번에 보기 좋은 수 |
| `AI_CHAT_MATCH_BATCH_SIZE` | 10 | 성향 비교 1회에 후보 10명 |
| `AI_CHAT_MAX_MATCH_CALLS` | 3 | 요청당 모델 호출 최대 4회(해석 1 + 비교 3)로 비용 상한 |
| `AI_CHAT_MATCH_MAX_OUTPUT_TOKENS` | 600 | 비교 결과는 similar/different 목록뿐 |

## 3. 장소·행사·일일 실행

| 변수 | 제안 | 이유 |
|---|---|---|
| `PLACES_PAGE_SIZE` | 10 | Kakao 최대 15 안에서 작성 화면에 충분 |
| `EVENT_SYNC_PROVIDERS` | `kopis,tour-api` | 확정된 연결 대상 둘. 운영 환경의 실제 연결 성공은 별도 확인 |
| `EVENT_SYNC_MAX_PERIOD_DAYS` | 31 | 두 제공처 공통 기술 상한 |
| `EVENT_SYNC_MAX_PAGE` | 5 | 하루 수집을 작게 시작 |
| `EVENT_SYNC_PAGE_ROWS` | 100 | 요청 수를 줄이려는 후보. 각 공급사 API별 실제 허용치를 확인 |
| `EVENT_SYNC_DAILY_PROVIDERS` | `kopis,tour-api` | 위와 같음 |
| `EVENT_SYNC_DAILY_TIME_ZONE` | `Asia/Seoul` | 한국 날짜 기준 |
| `EVENT_SYNC_DAILY_WINDOW_DAYS` | 31 | 오늘부터 한 달 앞 행사 |
| `EVENT_SYNC_DAILY_MAX_PAGES` | 5 | 제공처당 하루 최대 500건 |
| `EVENT_SYNC_DAILY_TIMEOUT_MS` | 15000 | 페이지 1건 호출 대기 상한 |
| `DAILY_SUMMARY_WORKER_MAX_INVOCATIONS` | 1 | 일일 실행 전체가 Edge 시간 한도 안에 끝나도록 worker는 1번만 |
| `DAILY_SUMMARY_WORKER_TIMEOUT_MS` | 75000 | worker 실행 시간(60초)보다 길게 |
| 일일 실행 시각 | 매일 00:01 Asia/Seoul | 사용자 결정 U4 |

**민규 확인:** 기존 일일 실행의 공개 정리 → 행사 수집 → worker 호출 구조와 배포 시간 한도를 점검한다. 일일 작업 등록 00:01은 유지하며 실제 실행을 나누는 기술안은 팀 검토한다. 별도 시각을 이 제안만으로 운영에 적용하지 않는다. 자동 완료·후기 공개를 일일 실행이나 모델 설정에 묶지 않는다.

## 4. AI 예산 원장 (U7)

원장은 “이 기간에 AI를 이만큼만 쓴다”는 상한이다. 호출 전에 예산을 예약하고 끝나면 실제 사용량으로 정산한다. 서버가 중간에 멈춰 사용량을 모르는 호출은 예약량 전체를 쓴 것으로 남긴다(초과 지출 방지). 교체 주기와 미정산 처리 기준은 아래 후보를 팀이 검토한다. 원장 교체를 미확인 사용량 삭제나 예산 상한 우회로 사용하지 않는다.

| 항목 | 제안 | 이유 |
|---|---|---|
| 합성 평가 원장(추가 지출 0원 근거 확인 후) | `ai-synthetic-eval-2026-10`, 호출 10회, 단위 100,000 | 합성 사례 10회 계획. 1회 최대 약 1만 단위(입력 바이트+출력 상한)로 넉넉히 잡고 10회로 막음 |
| 운영 원장 교체 주기 | **매월 1일 00:05 Asia/Seoul**에 새 원장 `ai-YYYY-MM` | 요금제·한도가 보통 월 단위이고, 중단 예약이 한 달 넘게 쌓이지 않음. 일일 실행(00:01)과 겹치지 않게 00:05 |
| 즉시 교체 조건 | ① 요금제·일일 한도 변경 ② 미정산 예약(`openCalls`)이 월 호출 한도의 5% 이상 ③ 장애로 서버가 반복 중단된 뒤 | 쓰지 않은 예산이 소진된 것으로 쌓여 AI가 일찍 꺼지는 것 방지 |
| 운영 호출 한도(월) | **요금제 월 허용량의 50%** (계정 자료로 계산) | 절반만 써서 요금제 초과·예상 밖 사용을 막음. 자료 전에는 운영 원장을 만들지 않음 |
| 운영 단위 한도(월) | 확인된 토큰 허용량의 50%. 토큰 한도가 없으면 “호출 한도 × 1회 최대 단위(약 1만)” | 위와 같음 |
| 이전 원장 | 보존기간·집계 범위·삭제 시점 팀 검토 | 원문 없는 비용 원장도 무기한 보존으로 확정하지 않음. 초기 운영 지표 영구 미저장과 구분 |

원장 설정은 service 권한으로 `configure_ai_budget_ledger(원장ID, 단위한도, 호출한도)`, 현황은 `get_ai_budget_ledger(원장ID)`로 본다(제안 SQL 01). 새 원장을 만든 뒤 환경값 `AI_BUDGET_LEDGER_ID`를 바꾸면 적용된다.
