## 2026-09-29 실제 로컬 Edge 검증 — PARTIAL

사용자의 진행 요청으로 전용 Supabase Edge·gateway에서 실제 기존 API를 검증했다. [7차 하네스](minkyu-edge-harness.json)의 총괄/A/B/C 범위만 수정했고 6차 미커밋 파일 중 이번 수정 범위 밖8개는 해시로 보존했다. 자세한 재현·결과·남은 사항은 [Edge 인계](requests/minkyu/2026-09-29-edge-handoff.md)에 있다.

- **실제 통과8묶음:** gateway 진입, 실제 Auth JWT 및 역할 분리, 앱 Origin거절/경로, 무료 공고 멱등·충돌·공개 투영, 양측 매칭과 당사자 정보, 내부secret 권한, 실행소스 보존, 로그 비밀/원문 제외.
- **미충족1개:** 로컬 Kong의 CORS plugin이 허용Origin GET응답을`*`로 바꾸고 OPTIONS를200/`*`/no-store 없이 반환한다. 앱의 exactOrigin·OPTIONS204 계약과 다르므로 전체 결과를 PARTIAL(exit2)로 기록한다. 미허용Origin의 앱403과 사용자/내부 인증은 유지됐다.
- **해결한 실행 문제:** 첫 gateway DNS503을 관찰한 뒤 전용환경을 같은 Edge설정으로 재기동해 API도달을 확인했다. CORS를 readiness와 독립 항목으로 검사하도록 runner를 보강해 실제 업무 검사를 끝까지 수행했다. 앱 코드나 생성된 gateway 설정을 바꿔 결과를 감추지 않았다.
- **새 도구:** `prepare_edge.py` + 회귀검사, 실제 gateway용 `edge_e2e.py`, CLI/Edge공식 근거 독립 검토. 정식SQL27개와 필요한 소스34파일만 준비하며 원본config는 보존하고 임시config만 Edge활성화한다.
- **추가 검사:** 준비 도구 Python10개 + 하네스6개 PASS, runner 구문/소스해시/수정경계 검사 PASS. TypeScript 앱은6차 이후 변경하지 않아 직전77개 Node검사를 반복실행하지 않았으며 이번 실제Edge검사와 구분한다.

실행환경은 CLI2.116.0·Edge Runtime v1.74.3·Kong2.8.1, 전용 DB는 적용SQL27개다. 가상 사용자·프로필·공고·작업 잔존0, 임시 비밀파일·CLI프로세스 정리 완료. 전용 Supabase와 Colima를 종료했으며 볼륨/이미지는 보존했다. 종현 추적89파일과 SQL27개 원문 일치, 총20개 미커밋 파일의 하네스 경계와 이전8파일 해시 보존도 확인했다. 원격환경을 변경하지 않았다.

**남은 작업:** 운영 gateway 대상을 정한 뒤 Origin·OPTIONS 정책 확인/설정·실제검증, 종현 검색 코어 도착 후 기본 GET검색 연결, PASS/문자/계좌공급사·외부모델·원격배포. 원격 관리형Edge/운영 CORS는 NOT_RUN이고 기본 검색은 아직405다. 이번 로컬결과를 운영배포 준비완료로 해석하지 않는다. 검증 후 사용자가 6차/7차 변경20파일의 커밋·푸시를 요청했다. 공유 대상은 `origin/minkyu/foundation-harness`이며 실제 커밋과 원격 반영은 Git 이력으로 확인한다.

- **완료:** GET 검색 query·caller 주입 방지·선택 정렬·익명 나이 권한·안전한 오류 변환, 명시된 executor에 실제 공통 인증/DB client를 조립하는 factory, CORS/requestId/no-store 유지, 기존 POST/내부 경로 보호.
- **완료:** 종현 실제 검색 모듈을 가상 RPC와 대조하는 `node tools/local/check_search_core.ts`. READY는 fixture 계약 호환이며 DB·배포 성공이 아니다.
- **연결 대기:** 현재 종현 코어 `bd15429`에서는 기본정렬·시작일순·익명기간·동표시·2필드µs커서 5개가 BLOCKED다. 익명 나이 거절과 민감 wire 부가 필드 거절 2개는 PASS다. 종현 파일을 수정해 진단을 억지로 통과시키지 않았다.
- **아직 미활성:** default fetch에는 검색 executor를 연결하지 않아 GET `/posts`는 기존405를 유지한다. 종현 수정본 검토/병합 후 기존 검색 service/repository를 연결하고 실제 GET→Auth→RPC를 검사한다. 가짜 검색 결과나 별도 검색 코어를 추가하지 않았다.

| [업무 API](../../backend/contracts/service-api.md) | 본인 조회/사진, 공고·신청, 양측 매칭, 채팅·알림, 완료·후기 | 무료 공고 지원; 사용자 경로는 로그인 필수 |
| [공고/매칭 DB](../../backend/contracts/core-service-db.md) | 등록 주소 비공개 저장, 동의 버전·재요청, 양측 확정 후 상세 정보, 일정 충돌 잠금 | 유료·계좌 효력 변경 정책 미정; 프런트엔드 연결 미실행 |
| [완료 DB](../../backend/contracts/completion-db.md) | 두 명 확인 후 수동 완료, 자동 완료 제외 조건, 알림과 상태 변경 원자성 | 실제 자동 처리 시각부터 완료·후기 7일 계산; 과거 이력 재작성 없음 |
| [후기 자동화](../../backend/contracts/review-automation-db.md) | 경험·후기 제출, 공개 조건, 명시적 숨김 보존, revision 무효화+outbox, 3개 이상 원문 요약 큐 | 칭찬 catalog 미정으로 비어 있음; 예약 실행·모델은 종현 연결 필요 |
| [작업 큐](../../backend/contracts/worker-jobs.md) | 중복 등록, SKIP LOCKED, lease·fencing·재시도 | review_summary만 지원; 운영 주기·재시도 수치 미확정 |
| [검색](../../backend/contracts/public-post-search-db.md) | 제목·장소/주소 검색, 검색 일치와 반환 권한 분리 | 종현 검색 경로 연결 필요; 주변/거리 검색 없음 |
| [요약 저장](../../backend/contracts/review-summary-db.md) | 적격 원문/revision, 전체 근거 조건부 게시·변경 무효화 | 외부 AI 생성·전체 흐름 검증 미실행 |

한쪽 완료 확인만으로는 완료되지 않는다. 자동 처리가 늦으면 예상 종료 시간이 아니라 **실제 자동 완료 처리 시각**부터 후기 7일을 계산한다는 사용자 결정을 적용했다. 후기 공개는 알림 이후 대기·분쟁 조건·양측 후기 또는 작성 기한 등의 DB 계약을 함께 검사한다. 기존 후기나 기존 완료 기록을 일괄 공개·변경하지 않는다.

수기 가입·단측 매칭·직접 채팅 INSERT 같은 우회 권한을 회수했다. 현재 참조 중인 필수 프로필 사진은 삭제를 차단하고 새 소유 사진으로 교체하도록 했다. 이 변경을 기존 프런트엔드에 적용하려면 새 API 호출 연결을 먼저 맞춰야 한다.

## 실제 검증

| 확인 | 결과 |
|---|---|
| Node 단위 | HTTP 11 + 인증/DB 14 + API 22 = 47개 PASS |
| Python 단위 | 가상 DB 계약 9 + 로컬 준비 17 + DB 실행 경계 2 + 하네스 6 = 34개 PASS |
| Deno | 2.9.6 `check:common`, `check:service` 및 최종 진입점 타입 검사 PASS |
| SQL 재생 | 정식 20 + 신규 6 = 26개, Supabase CLI 2.116.0 / PostgreSQL 17.6 PASS |
| rollback SQL | 작업 큐·검색·요약·양측 완료·후기 자동화·업무 API 6개 스위트 PASS |
| 독립 DB 세션 | 중복 enqueue, SKIP LOCKED claim, 게시/비공개 양방향 경합, 일정 중복 매칭, 양측 수동/자동 완료 경합 6개 PASS |
| 실제 JWT/HTTP | 실제 로컬 Auth 로그인·위조/역할 거절·무료 공고→신청→양측 매칭→완료→후기 공개/큐 등 8개 시나리오 PASS |
| 민감정보·정리 | API 로그에 토큰·키·후기/채팅 원문 없음, 가상 사용자·업무/큐 fixture 잔존 0 |
| 보존 | 원래 작업 폴더 332개 해시 일치, 기존 SQL 20개 변경 0, 실제 재생 신규 6개와 소스 해시 일치 |
| 협업 | 종현 파일 변경 0, 수정 허용 목록 중복 0, 이전 산출물 28개 보존 |

단위 합계 **81개**다. SQL 스위트·경쟁·HTTP 시나리오는 각각 별도로 센다. 실제 HTTP는 `createRuntimeHandler`를 독립 Deno 서버에서 실행하고 실제 Supabase Auth/PostgREST를 호출했다. 시간/원문 개수는 명시적 가상 DB fixture로 준비했다. 마지막 호스팅용 lazy default fetch 진입점은 추가 단위·타입 검사로 검증했다.

`NOT_RUN`: Supabase Edge 호스팅/gateway 실행, PASS·문자·은행 공급사, 외부 모델, 예약 실행기의 전체 연결, 프런트엔드, 원격 DB·운영 배포·부하 검사, 큐 잠금 대기 중 lease 만료의 별도 다중 세션 사례. `verify_jwt=false`는 service-api 자체 인증을 사용하기 위한 설정이며 인증 생략이 아니다. 호스팅 검증을 통과한 것으로 보고하지 않는다.

## 환경과 재현

Deno 2.9.6·Colima 0.10.3·Docker CLI 29.8.0·Node 25.9.0·Python 3.14.4를 사용했다. Homebrew Supabase 설치는 Command Line Tools 버전 요구로 실패하여 공식 npm CLI 2.116.0으로 검증했다. 시스템 개발 도구는 교체하지 않았다. PATH 점검의 supabase MISSING과 npx 실제 실행 성공은 구분한다.

[로컬 실행 안내](../../tools/local/README.md)에 재현 명령을 기록했다. 전용 Colima `yumidang-minkyu`, Supabase `yumidang-minkyu-db`, 임시 실행 루트 `/private/tmp/yumidang-minkyu-runtime-20260923-v5`를 사용했다. 기본 Docker context나 SSH·자동 시작 설정은 바꾸지 않았다. 검증 후 전용 Supabase와 Colima를 중지했으며 volume은 보존했다. 로컬 Auth admin의 가상 비밀번호 로그인은 운영 PASS/문자 로그인 구현이 아니다. 키·운영 데이터는 저장소에 넣지 않았다.

## 다음 담당과 보류

[3차 런타임 인계](requests/minkyu/2026-09-23-runtime-handoff.md)에 정확한 API·환경·종현 연결 요청을 기록했다. 이전 [2차 RPC 인계](requests/minkyu/2026-09-23-db-rpc-handoff.md)는 DB 계약 근거이며, 미연결 상태 설명은 이 문서가 최신이다.

- **종현담당:** 검색 repository/chatbot, 요약 모델·근거 검증/게시, 워커 점유/재시도, scheduled-jobs의 내부 maintenance 호출. 자기 파일에서 작업하고 민규 파일 변경은 요청 폴더에 남긴다.
- **민규 후속:** 공급사·자격 증명과 계약 확정 후 PASS/문자 세션·계좌 연결, 합의된 칭찬 목록 반영, 확정된 정책 구현, 호스팅/프런트엔드 연결과 배포 검증.
- **합의 필요:** 계좌 효력 변경 후 최종 동의, 분쟁 세부 판단, 기존 수동 완료자의 분쟁 제한, 칭찬 키워드와 운영 배치/재시도 값. 임의 결정하지 않았다.

이번 작업의 진행률은 [진행표](minkyu-progress.md)에 기록한다. 전체 백엔드 출시율로 해석하지 않는다.

## 다음 대화에서 재개할 순서

이 절은 “민규 담당 전체가 끝났는가”, “남은 작업 전에 내가 준비할 것이 있는가” 대화와 “여기까지 커밋·푸시하고 이어서 할 일을 기록해 달라”는 요청의 기록이다. 새 공급사나 정책은 이 대화에서 선택·확정하지 않았다.

### 민규가 직접 준비할 사항

| 항목 | 필요한 준비 | 현재 확인 상태 |
|---|---|---|
| PASS 본인인증 | 보유 업체 계정 확인 또는 업체 선정, 이용 신청/계약, 테스트 이용 권한·공식 문서 확보 | 업체·계약·접근 권한 미확인 |
| 문자 로그인 | 보유 문자 업체 확인 또는 선정, 발송 계정, 해당 업체가 요구하는 발신번호 등록 | 업체·발신번호·접근 권한 미확인 |
| 계좌 인증 | 본인 명의 확인 가능한 제공사 선정, 테스트 이용 권한·연동 문서 | 업체·검증 방식·접근 권한 미확인 |
| 배포 환경 | 사용할 Supabase 프로젝트 지정/생성, 필요한 접근 권한, 비용 한도·서비스 URL 확인 | 사용할 프로젝트·예산 미확인 |
| 서비스 정책 | 아래 미정 규칙 결정 | 아직 결정되지 않음 |

업체별 서류·사업자 자격·심사·계약 요구는 선정 후 공식 자료로 확인한다. 특정 업체 계약이 반드시 가능하거나 사업자 조건이 동일하다고 가정하지 않는다. 기존 계약이나 프로젝트가 있으면 먼저 재사용 가능성을 확인한다. 민규가 직접 코딩하거나 서버를 설정할 필요는 없으며 기술 구현·설정·검증은 AI 작업으로 이어간다. 비밀키는 채팅·Git에 붙이지 않고 로컬 비밀 설정 또는 배포 환경 Secrets로 관리한다.

### 결정이 필요한 정책

- 등록·신청 후 계좌 인증 효력이 사라지면 최종 매칭을 허용할지.
- 분쟁 접수·판정·해제 기준과 완료 확인한 사람의 분쟁 접수 허용 여부.
- 후기 칭찬 버튼의 실제 키워드 목록.
- 확정 취소, 미선정 신청 종료, 공고 수정·마감·삭제의 남은 규칙.
- 운영 배치 주기·재시도 설정은 기술 제안과 서비스 결정을 구분해 확정한다.

자동 완료의 실제 처리 시각부터 후기 7일을 계산하는 규칙은 이미 확정·구현했으므로 다시 미정으로 되돌리지 않는다. 플랫폼 결제·대금 보관·정산·자동 환불을 추가하는 계획은 없다.

### 다음 실행 순서

1. 현재 Git 상태·원격 브랜치·종현 요청을 읽고 민규 작업자를 유지한다. 이 구현의 커밋을 새 기준으로 삼아 다음 작업의 정확한 수정 목록을 분리한다. 종현 코드에 직접 쓰지 않는다.
2. 커밋된 신규 SQL 6개가 이제 정식 이력인 점을 반영해 로컬 준비 도구/테스트를 갱신한다. 현재 `prepare_database.py`는 20개 정식+6개 미커밋 SQL 전용이라 커밋 후에는 중복 버전으로 거절한다. 이것을 DB 실패로 오해하지 않는다. 기존 하네스도 이전 HEAD에만 맞는 기록이다.
3. 준비 현황은 먼저 업체 이름·보유 계정·Supabase 프로젝트 유무만 확인한다. 키 자체를 대화로 요청하지 않는다. 아직 없다면 공급사와 무관한 인증 상태 전이·실패 처리·인터페이스·테스트, 로컬 Edge 기동/gateway 검증과 배포 구성 준비부터 진행할 수 있다.
4. 공급사 확정 후 공식 연동 문서를 검증하고 민규 소유 identity/phone/bank adapter, signup/verification, 세션 발급·복구, 유료 업무 경로를 연결한다. 명시적 검증 근거 없이 성공으로 처리하지 않는다.
5. 합의된 정책을 DB·API·테스트에 반영한다. 종현에게 검색/AI/워커/예약 실행 연결은 기존 3차 인계 문서로 전달한다. 실제 전체 연결 검증은 별도 수행한다.
6. 로컬/테스트 환경에서 실제 연결을 검증한 뒤 원격 마이그레이션·배포의 대상과 변경안을 준비한다. 이번 커밋·푸시 요청은 운영 DB 변경이나 서비스 배포까지 승인한 것이 아니다.

미완료 업무 전체를 지금 당장 진행하라는 새 지시는 아직 없다. 이번 대화의 실행 범위는 현재 산출물과 이 재개 기록의 커밋·푸시다. 다음 요청에서는 이미 완료한 핵심 API를 다시 골격부터 만들거나 100%를 전체 완료로 보고하지 않는다.
